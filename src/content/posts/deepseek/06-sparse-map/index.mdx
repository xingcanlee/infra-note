前面三篇把「每个 token 在缓存里占多宽」从 40960 个数压到 576 个。但第 02 篇的公式里还有一个因子没动过：

$$
\text{总字节} = \underbrace{(d_c + d_r)}_{\text{04、05 篇压的}} \times \underbrace{L}_{\textbf{还没动}} \times n_{\text{layers}} \times \text{bytes}
$$

而且更要紧的是**时间**：decode 每生成一个 token，都要把全部 $L$ 行历史读一遍。序列越长，每个 token 越慢。缓存压窄只是把这条曲线的斜率降低，没有改变它仍在增长。

这一篇不讲某个具体机制，而是搭一个坐标系：**所有稀疏注意力都在改「位置 $t$ 允许读哪些 $s$」，区别只在改法**。读完你能用三个指标分类任何一篇稀疏注意力论文，并预判它的代价落在哪里。

## 先看一个例子：两种「省一半」

把第 01 篇的因果掩码换成「滑动窗口 w=2」和「跨步 2」，都省掉了一部分读取：

<AttentionGrid client:visible mask="swa" showOutput={false} title="图 06-1a：滑动窗口 w=2——只读最近 2 个位置" />

<AttentionGrid client:visible mask="strided" showOutput={false} title="图 06-1b：跨步 2——每隔一个位置读一个，外加当前位置" />

两者在 $L=8$ 时的密度分别是 41.7% 和 66.7%，看起来窗口「更省」。但这是个陷阱：

- 窗口：每行最多读 **2** 个，$L$ 变成 100 万也还是 2 个。
- 跨步：每行最多读 $\lceil L/2\rceil$ 个，**随 $L$ 一起长**。

对 decode 来说后者几乎没有帮助——它降低了常数，没有改变增长阶。**所以「省了多少」不是最重要的指标，「每步代价有没有上限」才是。**

## 三个指标

这是本篇要交付的思维工具。任何稀疏注意力机制都可以用这三项描述：

| 指标             | 定义                                   | 它决定什么                                   |
| ---------------- | -------------------------------------- | -------------------------------------------- |
| **密度**         | 可读格子数 / 因果可读格子数            | prefill 的总计算量省多少                     |
| **单步代价上限** | 单个 $t$ 最多读几个位置                | decode 每个 token 的代价是否随 $L$ 增长      |
| **可达范围**     | 一层（或若干层）后能看到的最早位置     | 远处的信息还拿不拿得到——质量的上限在这里     |

三者互相制约：**压低单步代价必然压缩可达范围**，除非额外加一条分支去补。后面几篇的全部花样都是在这个三角里取舍。

同一份数据的表格形式（$L=8$，可达范围按最后一个位置算）：

| 机制          | 密度   | 单步代价上限  | 单层可达 | 4 层后可达 | 性质                                     |
| ------------- | ------ | ------------- | -------- | ---------- | ---------------------------------------- |
| 因果（全读）  | 100%   | 8（随 $L$ 长）| 0        | 0          | 基线：什么都不省，什么都能看到           |
| 滑动窗口 w=2  | 41.7%  | **2**（封顶） | 6        | 3          | 单步代价有上限，但远处要靠叠层传递       |
| 窗口 + 锚点   | 58.3%  | **3**（封顶） | **0**    | 0          | 加一个前缀锚点，单层就能看到开头         |
| 选块 2×1      | 33.3%  | **2**（封顶） | 6        | **6**      | 块内对齐，但叠层也传不出去（见下文）     |
| 跨步 2        | 66.7%  | 5（随 $L$ 长）| 0        | 0          | 密度不低，却没有封顶——对 decode 帮助有限 |
| top-k 打分    | 41.7%  | **2**（封顶） | 4        | 0          | 形状随输入变化，按内容挑                 |
| 多分支并集    | 66.7%  | **4**（封顶） | 4        | 0          | 窗口 + 选块，兼顾近处与远处              |

三个值得停下来看的地方：

**① 跨步 2 的密度（66.7%）比窗口（41.7%）高，但对 decode 更没用。** 因为它没有封顶。这再次说明密度和单步代价是两个独立的轴。

**② 选块 2×1 叠 4 层后的可达范围还是 6，完全没有改善。** 原因：当 `keep=1` 时每个位置只能读自己所在的块，而块内的位置也只能读本块——信息根本跨不过块边界。**叠层补偿不是万能的**，它要求读取集合之间有重叠。窗口有重叠（位置 $t$ 和 $t-1$ 的窗口相交），所以能传；这种选块没有，所以传不出去。

**③ top-k 的形状随输入变化。** 前六种是固定模式，掩码只取决于位置；top-k 取决于内容。这是「静态稀疏」与「动态稀疏」的分界——动态的能挑到真正相关的远处位置，代价是打分本身要花钱（第 09 篇 DSA 的主题）。

### 叠层补偿到底能走多远

「窗口虽小，叠层就能看远」这个说法常被当作定论。用真实量级算一下就知道它的限度——窗口 $w=4$、序列 $L=4096$、看最后一个位置：

| 层数 | 能间接看到的最早位置 |
| ---- | -------------------- |
| 1    | 4092                 |
| 2    | 4089                 |
| 8    | 4071                 |
| 32   | 3999                 |
| 61   | **3912**             |

**61 层之后也只倒推了 184 个位置**，离序列开头（位置 0）差着 3912 个。可达范围大致按 $(w-1)\times n_{\text{layers}}$ 线性增长，而上下文长度是独立变大的——所以纯窗口注意力在长上下文上必然丢信息。

这就解释了为什么真实机制几乎都是**多分支**：窗口负责近处的精细度，另一条分支（锚点、选块、top-k）负责把远处拉进来。单一模式解决不了这个三角。

顺便，同一组数字也说明窗口的密度随 $L$ 迅速下降：

| $L$  | 窗口 $w=4$ 的密度 | 单步代价上限 |
| ---- | ----------------- | ------------ |
| 16   | 42.65%            | 4            |
| 64   | 12.02%            | 4            |
| 1024 | 0.78%             | 4            |
| 4096 | 0.20%             | 4            |

密度趋于 0，单步代价恒为 4。这正是「封顶」的含义。

## 统一接口

把读取集合写成一个函数，所有机制就能共用同一套代码、同一个动画、同一组指标。本站的定义在 `src/explainers/core/masks.ts`，文章与动画用的是同一份：

```ts
/** 位置 t 是否允许读取位置 s。true = 可读。 */
export type MaskFn = (t: number, s: number, l: number) => boolean;

export const causal: MaskFn = (t, s) => s <= t;

export const slidingWindow = (w: number): MaskFn => (t, s) => s <= t && t - s < w;

export const windowWithSink = (w: number, nSink = 1): MaskFn =>
  (t, s) => s <= t && (t - s < w || s < nSink);

export const blockSelect = (blockSize: number, keep: number): MaskFn => (t, s) => {
  if (s > t) return false;
  return Math.floor(t / blockSize) - Math.floor(s / blockSize) < keep;
};

/** 多分支机制 = 若干读取集合的并集 */
export const union = (...fns: MaskFn[]): MaskFn => (t, s, l) => fns.some((f) => f(t, s, l));
```

三个指标同样是几行：

```ts
/** 相对因果基线的密度 */
export function maskDensity(l: number, fn: MaskFn): number {
  let kept = 0;
  const total = (l * (l + 1)) / 2;
  for (let t = 0; t < l; t++) for (let s = 0; s <= t; s++) if (fn(t, s, l)) kept++;
  return kept / total;
}

/** 每一行实际读取的位置数——取 max 就是单步代价上限 */
export function rowCounts(l: number, fn: MaskFn): number[] { /* … */ }

/** 可达范围：用可达性（BFS）算 nLayers 层后能看到的最早位置，而不是用 w × 层数估算 */
export function receptiveField(l: number, fn: MaskFn, t: number, nLayers: number): number {
  let reach = new Set<number>([t]);
  for (let layer = 0; layer < nLayers; layer++) {
    const next = new Set<number>(reach);
    for (const p of reach) for (let s = 0; s <= p; s++) if (fn(p, s, l)) next.add(s);
    reach = next;
  }
  return Math.min(...reach);
}
```

`receptiveField` 用真实可达性而不是公式估算，正是为了暴露上面「选块传不出去」那种情况——按 $w\times n_{\text{layers}}$ 估算会给出错误的乐观结论。

## 代价与边界

- 三个指标都是**结构性**的，只依赖掩码形状，不依赖权重。它们能预判代价，但不能预测质量：一个机制可能单步代价很低、可达范围也够，质量却因为「挑错了位置」而下降。
- 密度低不等于实际更快。稀疏带来的不规则访存可能让 kernel 效率下降，小规模下甚至比全读更慢。真实收益要看是否有对应的 kernel 实现（第 18 篇）。
- 动态稀疏的掩码依赖输入，因此每步都要重新算读取集合。这笔开销必须算进总账——它是第 09 篇的核心议题。
- 可达范围的计算假设「只要读了就能传递信息」。实际上注意力权重可能很小，信息传递是衰减的。所以可达范围是**上界**，不是保证。
- 本篇所有数字都是对给定掩码的精确计算，不是本机性能实测。

## 自测

1. 一个机制密度 50%、单步代价上限随 $L$ 增长；另一个密度 80%、单步代价封顶在 64。对 decode 更有价值的是哪个？为什么？
2. 为什么「选块 2×1」叠层也扩不出去，而「滑动窗口」能？从读取集合的重叠关系解释。
3. 窗口 $w=8$、61 层。要让最后一个位置能间接看到序列开头，$L$ 最大能是多少？
4. 静态稀疏和动态稀疏的分界是什么？动态的额外成本出现在哪一步？
5. 动手：在 `toy.py` 里组合 `windowWithSink(4, 2)` 与 `blockSelect(8, 2)` 的并集，算出三个指标。它比单用窗口好在哪，代价是什么？
