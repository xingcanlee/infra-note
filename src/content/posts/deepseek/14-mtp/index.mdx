上一篇把参数问题解决了：671B 参数，每个 token 只激活 37B。但还有一个结构性的限制没动——**一次前向只出一个 token**。

生成 1000 个 token 就要跑 1000 次完整的模型前向。而第 02 篇说过，decode 是**带宽受限**的：每次前向都要把全部权重和 KV cache 读一遍，算术量却很小。既然每次都要把权重搬一遍，**能不能一次多产出几个 token，把这笔搬运摊薄？**

读完你能回答：MTP 模块长什么样、它在训练和推理时扮演的两个完全不同的角色、以及为什么推测解码**不会改变输出**。

## 先看一个例子

推测解码的流程：一个便宜的草稿模块先猜几个 token，主模型跑**一次**前向把它们全部验证，从第一个猜错的地方截断。

<SpecDecodeView client:visible title="图 14-1：草稿提出 2 个，主模型一次验证——注意第 3 轮猜错时发生了什么" />

关键在验证那一步：**主模型一次前向就能检查全部候选**。因为候选构成一个序列，可以像处理 prompt 一样并行打分——这正是 prefill 和 decode 的区别（第 02 篇）。推测解码的本质是**把 decode 伪装成一次小型 prefill**。

三种结果：

| 情况 | 产出 |
| --- | --- |
| 全部 $k$ 个都对 | $k+1$ 个（还白拿一个：验证时主模型已经算出了下一个 token 的分布） |
| 前 $j$ 个对、第 $j{+}1$ 个错 | $j+1$ 个（错的那个由主模型自己的结果顶上，同样是免费的） |
| 第一个就错 | 1 个（退化成普通 decode，没有损失） |

**最差情况也不比普通 decode 慢**（忽略草稿本身的开销）。这是推测解码能被放心使用的原因。

## 机制

### MTP 模块的结构

DeepSeek-V3 用 $D$ 个**顺序连接**的 MTP 模块预测 $D$ 个额外 token。第 $k$ 个模块由四部分组成（§2.2）：

| 部分 | 是否共享 |
| --- | --- |
| embedding 层 $\mathrm{Emb}(\cdot)$ | **与主模型共享** |
| 输出头 $\mathrm{OutHead}(\cdot)$ | **与主模型共享** |
| Transformer block $\mathrm{TRM}_k(\cdot)$ | 本模块独有 |
| 投影矩阵 $M_k\in\mathbb{R}^{d\times 2d}$ | 本模块独有 |

共享 embedding 和输出头意味着**额外参数很少**——只有一个 Transformer block 和一个投影矩阵。V3 实际取 $D=1$（§4.2），即只多预测一个 token。

### 公式

第 $k$ 个深度把上一深度的表示和未来 token 的 embedding 拼起来投影（式 (21)）：

$$
\mathbf{h}_{i}^{\prime k}=M_{k}\big[\mathrm{RMSNorm}(\mathbf{h}_{i}^{k-1});\ \mathrm{RMSNorm}(\mathrm{Emb}(t_{i+k}))\big]
$$

$k=1$ 时 $\mathbf{h}_i^{k-1}$ 就是主模型的输出表示。然后过本模块的 Transformer block（式 (22)），再用共享输出头得到分布（式 (23)）：

$$
\mathbf{h}_{1:T-k}^{k}=\mathrm{TRM}_{k}\big(\mathbf{h}_{1:T-k}^{\prime k}\big),\qquad
P_{i+k+1}^{k}=\mathrm{OutHead}\big(\mathbf{h}_{i}^{k}\big)
$$

**注意式 (21) 里的 $\mathbf{h}_i^{k-1}$**：第 $k$ 个模块吃的是第 $k-1$ 个模块的输出，不是主模型的输出。模块是**串起来的**，不是并排挂在主干上的。

### 为什么要串联

论文明确对比了另一种做法（Gloeckle et al.）：用 $D$ 个**独立的输出头并行**预测 $D$ 个未来 token。DeepSeek-V3 选择顺序预测，理由是**在每个预测深度保留完整的因果链**（§2.2、图 3）。

差别在于：并行预测时，「第 2 个未来 token」的预测看不到「第 1 个未来 token」是什么；而串联时，第 2 个模块的输入里包含了 $t_{i+1}$ 的 embedding——它知道前一个猜的是什么。

这对推测解码特别重要：草稿序列内部必须自洽，否则第 2 个候选的命中率会很低。

### 训练目标

每个深度算一个交叉熵（式 (24)），跨深度平均后乘权重 $\lambda$（式 (25)）：

$$
\mathcal{L}_{\mathrm{MTP}}=\frac{\lambda}{D}\sum_{k=1}^{D}\mathcal{L}_{\mathrm{MTP}}^{k}
$$

$\lambda$ 是分阶段的：前 10T 个训练 token 用 $\lambda=0.3$，之后 4.8T 个用 $\lambda=0.1$（§4.2）。前期权重大、后期调小——让模型先获得这个额外监督信号的好处，后期再把重心交还给主目标。

### 两个完全不同的角色

这是本篇最该记住的一点。**MTP 在训练和推理时做的是两件事**：

| | 训练时 | 推理时 |
| --- | --- | --- |
| 输入的未来 token | **真实文本**（teacher forcing） | 上一个模块猜的 |
| 作用 | 额外的监督信号，**改善主模型本身** | 当草稿模块，加速生成 |
| 可否丢弃 | — | **可以**，丢掉后主模型照常工作 |

论文在 §2.2「MTP in Inference」明确说：推理时可以**直接丢弃** MTP 模块，主模型独立正常运行；也可以留着做推测解码。

§4.5.1 的消融（表 4）正是利用了这一点：对照组和实验组**推理成本完全相同**（因为都把 MTP 丢掉了），差别只在训练时有没有这个额外目标。结论是 MTP 在大多数 benchmark 上提升了性能。

**所以 MTP 首先是一个训练技巧，其次才是一个推理加速手段。** 把它只当成「推测解码的草稿模型」会漏掉一半。

### 论文给的数字

§5.4.3：V3 用 MTP 预测接下来的 2 个 token，第二个 token 的接受率在不同生成主题上是 **85%–90%**，由此达到 **1.8× TPS**。

用本篇的期望公式核对一下（$k=1$，即多猜 1 个）：

$$
\mathbb{E}[\text{每轮产出}] = (1-p)\cdot 1 + p\cdot 2 = 1+p
$$

$p=0.85$ 时是 1.85，$p=0.90$ 时是 1.90。**和论文的 1.8× 对得上**——这说明那个 1.8× 基本就是「接受率直接转化成的前向效率」，没有额外的隐藏开销，也没有被低估。

注意论文只说了「various generation topics」，没有给出主题列表、采样参数或硬件条件。接受率依赖具体内容：代码和格式化文本通常好猜，开放式创作难猜。

## 代码实现

> 完整可运行脚本见文章目录下的 `toy.py`。

核心是验证循环——**输出与逐个生成完全相同**这条性质，脚本里是用 `assert` 保证的：

```python
def speculative_decode(truth, k, hits):
    """truth: 主模型真正会生成的序列。返回 (输出, 主模型前向次数)。"""
    out, forwards, hit_i = [], 0, 0
    while len(out) < len(truth):
        base = len(out)
        n = min(k, len(truth) - base)

        # ① 草稿：便宜地提出 n 个候选
        draft = []
        for j in range(n):
            ok = hits[hit_i % len(hits)]; hit_i += 1
            draft.append(truth[base + j] if ok else f'？{base + j}')

        # ② 验证：主模型一次前向检查全部候选
        forwards += 1
        accepted = 0
        for j in range(n):
            if draft[j] == truth[base + j]:
                accepted += 1
            else:
                break

        # ③ 提交：接受的前缀 + 一个免费 token
        out.extend(truth[base:base + accepted])
        if len(out) < len(truth):
            out.append(truth[len(out)])      # 全中→奖励 token；有拒→主模型的纠正
    return out, forwards
```

输出：

```
目标序列 10 个 token

草稿质量                 前向次数      前向效率        输出是否正确
全中 (p=1.0)              4     2.50×           ✓
好 (p≈0.83)              4     2.50×           ✓
一般 (p=0.5)              5     2.00×           ✓
全错 (p=0.0)             10     1.00×           ✓
不用推测解码                 10     1.00×           ✓

四种草稿质量下的输出完全一致 ✓ —— 推测解码不改变结果

V3 的配置（k=1）：
  接受率 85% → 每轮期望 1.85 个 token
  接受率 90% → 每轮期望 1.90 个 token
  论文报告 1.8× TPS，与此一致
```

两处值得注意。

**「全错」那一行**：草稿全错时退化成普通 decode，而不是更慢。代价只是白跑了草稿模块——而草稿很便宜，这正是整个方案的安全边际。

**$k=2$ 时「全中」和「好」的前向次数相同（都是 4）**：因为有奖励 token，全中的一轮产出 3 个；而偶尔猜错一次，那一轮产出 2 个——在 10 个 token 这种短序列上还没拉开差距。接受率的影响要在长序列上才充分体现。

### 真实实现在哪

MTP 模块在权重里是独立的一层。`README_WEIGHTS.md` 给出的组织方式：

| 事实 | 位置 |
| --- | --- |
| `num_nextn_predict_layers` 表示 MTP 模块数，开源 V3 权重含 **1 个** | `README_WEIGHTS.md:6` |
| 权重分为 Main Model Weights 与 MTP Modules 两部分 | `README_WEIGHTS.md:13` |
| MTP 模块的 layer ID **紧接在主模型之后**：`num_hidden_layers=61` 时 MTP 的 ID 是 61 | `README_WEIGHTS.md:55-56` |

「layer ID 是 61」这个细节很说明问题：**MTP 在权重布局上就是第 62 层**，加载时按层号取；要丢弃它，不加载这一层即可。这就是「推理时可以直接丢弃」在工程上的含义。

本地快照的 `inference/model.py` 里**没有** MTP 的实现——参考实现只包含主模型。想读 MTP 的推理代码要去看支持它的推理框架。

## 代价与边界

- 推测解码省的是**前向次数**，不是计算量。草稿模块本身要跑，验证时并行打分的算术量也比单 token decode 大。它赚的是「把带宽受限的多次前向，换成算力受限的一次前向」。
- 收益完全取决于接受率，而接受率依赖内容。论文的 85%–90% 绑定其模型与测试主题，不能照搬。
- $D$ 越大不一定越好：串联模块越深，后面的猜测越不准，收益递减（`toy.py` 里验证了这一点）。V3 只取 $D=1$。
- MTP 增加训练成本和少量参数。消融（表 4）证明它改善质量，但那是在论文的训练配置下。
- 本机没有 GPU，本篇不做任何速度实测；1.8× 是论文数字，上面的期望计算只是与之核对一致性，不是独立验证。
