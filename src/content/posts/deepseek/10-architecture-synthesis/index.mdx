前九篇把 Roofline 访存模型、MLA 潜空间吸收、稀疏索引与压缩、DeepSeekMoE、Engram 静态记忆、mHC 多分支超连接和 MTP/DSpark 一块块拆开了。到了真正上线服务的那一刻，这些部件必须严丝合缝地跑在同一个静态图与通信排期里。

本篇用三幅全景图把所有拼图串成整机视图：先看 **1 个解码 token** 在单个 DeepSeek-V4.1 层内走完的六阶段字节账本；再拉高视角，核对 V2 到 V4.1 五代架构的 KV Cache 与参数收敛轨迹；最后进入 `UBatchContext`（DBO）双微批集群流水线，对比 NVIDIA GPU（`vllm@bb23c0a8`）与昇腾 NPU（`vllm-ascend@3649b8ff`）的完整落地闭环[^vllm-synth][^ascend-synth]。

## 单 Token 解码全景：V4.1 层内六阶段与字节账本

跟普通 Transformer 单流残差不同，DeepSeek-V4.1 的主干在层间传递四条并行流形残差 `[T, 4, d]`。为了压榨 HBM 带宽并控制算力屋脊，每走完一个解码层，张量都要经过严格编排的「聚合—稀疏检索—记忆合流—分散—回写」六步闭环（图 1）：

/>

结合图 1 与 `vllm/models/deepseek_v41/nvidia/model.py`（`L560-725`）及 `vllm_ascend/models/deepseek_v41/model.py`（`L772-940`），六个阶段的张量流转与算子绑定如下：

1. **阶段 1：`mHC Pre-Mix`（`[T, 4, d] -> [T, d]`）**：先用 Sinkhorn 双随机权重从 $4$ 条分支残差聚合成单流输入。未开启 DBO 且 `hidden_size % 1024 == 0` 时，GPU 由 `mhc_shifted_post_pre_deep_gemm` 融合上一层 post 与本层 pre（单遍读写），NPU 调 `torch.ops._C_ascend.npu_hc_pre_v3`[^vllm-synth][^ascend-synth]。
2. **阶段 2：`CSA / Sparse MLA`（`288 B` Paged KV Gather）**：在 `DeepseekV4SparseMLABackend`（GPU）与 `AscendDSAV41Impl`（NPU）中，头部维度收缩到 `512 = 448 NoPE + 64 RoPE`。经压缩器与闪电索引器（`DeepseekV4Indexer` / `npu_quant_lightning_indexer_v3`）按候选块过滤出稀疏历史槽位后，每层仅按 **`288 B/token`**（NVFP4 压缩记录）读取高频长文槽位。
3. **阶段 3：`Async Engram Gate Add`（第 `1`、`14` 层特定旁路）**：这两层在 `mhc_post` 回写四分支之后、下一层 `mhc_pre` 之前原位介入。由于行索引在第 $0$ 层前已由奇数乘数与 $K=8$ 素数哈希确定，计算流只需等待异步预取事件（`cuda.Event` 或 `torch.npu.ExternalEvent`），再用 `4d:1d` 投影与有符号开方 `RMSNorm` 门控更新 `[T, 4, d]`。
4. **阶段 4：`DeepSeekMoE`（共享 + `Top-8` 路由 Dispatch / GMM / Combine）**：门控路由带无辅损动态偏置 `e_score_correction_bias` 选出热点均衡的少数细粒度专家，与常驻共享专家并跑。跨卡走 `DeepEP` `EPBuffer` 或昇腾 `TokenDispatcherWithMC2`（`npu_moe_distribute_dispatch_v2`），本地对齐分块后调用分组矩阵乘再归位。
5. **阶段 5：`mHC Post-Mix`（`[T, d] -> [T, 4, d]`）**：将 MoE 输出按流形约束权重 `H_post` 与双随机转移矩阵 `H_res` 写回四条残差通道，保证跨越几十层连乘后的信号范数 `Amax` 始终受控在安全区间（见[08 流形受限超连接（mHC）](../08-mhc/)）。
6. **阶段 6：`DSpark Draft`（单次 3 层 SWA + 低秩马尔可夫验证头）**：主干多层隐状态通过 `context_wkv_proj` 送入 3 层滑动窗口草稿网络并行产 logits，再由 `r=256` 的 `DSparkMarkovHead` 与 `DSparkConfidenceHead` 连采并按全局配额截断，最后经无损拒绝采样一次步进多 token[^v41-flash]。

## 从 V2 到 V4.1-Flash：五代演进与双硬件闭环

拉回全局视角，DeepSeek 每一代模型几乎都在围着同一个系统目标转：**在不损长上下文推理能力的条件下，同时打穿 KV Cache 容量墙与 Decode HBM 带宽墙**。图 2 用等比字节尺标汇总了五代演进与两大算力底座的对应实现：

![DeepSeek 五代 KV Cache 与双硬件执行全貌](./diagrams/10-five-gen-ledger.drawio '图 2：从 V2 到 V4.1-Flash 每词元 KV 字节账本演化与 SM100 / Ascend 910 双硬件闭环')

对照图 2 中的核心指标与源码约束，五代技术路线的协同关系一目了然：

| 模型代际                    | 注意力与 KV 压缩机制                      | 单层每 Token KV 字节               | 稀疏与推测关键机制                                                         |
| --------------------------- | ----------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------- |
| **V2 / V3 / R1**            | MLA（`512` latent + `64` RoPE，BF16）     | **`1,152 B`**                      | V2 细粒度 MoE；V3 无辅损偏置 + 因果 MTP 链                                 |
| **V3.2**                    | MLA + DSA 闪电索引器（`index_topk` 选块） | **`576 B`**（FP8 裸负载）[^v32-kv] | `Dense -> Sparse` 选块注意力；Hopper tile 实装含标尺为 `656 B`[^v32-kv]    |
| **V4 / V4.1（生产 634B+）** | 压缩器 + 稀疏 MLA（`448 NoPE + 64 RoPE`） | **`288 B`**（NVFP4 压缩记录）      | 4 流 `mHC` + 两层主机卸载 `Engram` + `DSpark`（V4.1-Flash 扩至 `196B` 表） |

- **每 token KV 足足压到四分之一**：从 BF16 MLA 的 `1,152 B`（`576 * 2 B`），经 FP8 稀疏化降到 `576 B`，再到 V4.1 的 NVFP4 `288 B`（`448 / 2 = 224 B` 载荷 + `64 B` 缩放与 RoPE）。再叠加共享 KV 源层（`is_kv_source` / `DeepseekV41Topology`）后，超长上下文下的单并发内存压力降幅可达数量级。
- **双硬件的等语义闭环**：NVIDIA SM100 路线依靠 FP4/FP8 `DeepGEMM`、CuTe mHC 边界核、`DeepEP` RDMA/对称内存直读与 `FULL` CUDA Graph；华为 Ascend 路线则由 `AscendDSAV41Impl`、`npu_hc_pre_v3`、`TokenDispatcherWithMC2`、$2^{22}$ 分块 UVA 主机表（`HostUvaBuffer`）和 `ACLGraphWrapper` + `ExternalEvent` 组成对等生态。

## 集群级 DBO（Dual-Microbatch）与异步 Engram 时间线

单卡算子做完融合之后，多机多卡 EP 推理的最大头疼问题是**通信裸露时间**：如果整个批一次性跑完 Attention 再堵在 `All-to-All` Dispatch 上等数据跨机搬运，期间昂贵的矩阵计算单元只能干等。

`vllm/v1/worker/ubatching.py`（`L1-90, 165-254`）与 `vllm/models/deepseek_v41/nvidia/model.py`（`L781-805, 1151`）把每个全局批切分成一对乒乓微批 **`uBatch 0`（`μB0`）与 `uBatch 1`（`μB1`）**，用两条 CUDA 流与事件屏障把通信完全盖在计算下面。图 3 按严格毫秒等比刻度展示了这一调度切换过程：

顺着图 3 的毫秒刻度看清三个工程要点：

1. **计算流与通信流的毫秒级错峰互掩**：串行基线依次执行两份微批与预取等待共耗时 **`15.2 ms`**。切入 DBO 稳态后，`μB0 Dispatch`（`1.4..3.2 ms`）掩盖在 `μB1 Attention` 下，随后通信流接力 `μB1 Dispatch`、`μB0 Combine` 与 **`μB1 Combine A2A`（`7.6..9.4 ms`）** 并分别由 `MoE` 与下层 `Attention` 遮掩，稳态步长压至 **`9.4 ms`（提速 `1.62x`）**。
2. **异步 Engram 预取贴身同行**：由于第 `1`、`14` 层的 Engram 哈希在层前即已知，后台流早在第 $0$ 层开始的同时就把 `6.0 ms` 主机表 DMA 搬运放飞，完美藏进多层计算与微批间隙里；同时 `EngramModelState` 与 `attn_metadata` 按 `dbo_current_ubatch_id()` 严格隔离 `ubatch_idx = 0 / 1`，避免双微批串写。
3. **DBO 开启时的算子退避规则**：正如 `vllm/models/deepseek_v41/nvidia/ops/mhc.py`（`L57`）所示，当 `parallel_config.use_ubatching` 开启时，引擎主动关闭跨层 `mhc_shifted_post_pre` 融合——因为 `μB0` 与 `μB1` 在 MoE 边界交错让路，不能在单微批内把上一层 post 和本层 pre 绑成同一段静态流水。

## PyTorch / NumPy 核心验证：五代 KV 字节与 DBO 时序核算

下面这段自包含 Python 脚本精确复算了图 2 的三档 KV 字节规格与图 3 的串行/DBO 毫秒级调度加速比：

```python
import numpy as np

kv_v23_bf16 = 512 * 2 + 64 * 2   # 1152 B/layer
kv_v32_fp8 = 512 * 1 + 64 * 1    # 576 B/layer
kv_v41_fp4 = 448 // 2 + 64       # 224 B FP4 + 64 B scale/RoPE = 288 B/layer
assert kv_v23_bf16 == 1152 and kv_v32_fp8 == 576 and kv_v41_fp4 == 288

attn, disp, gmm, comb, engram_wait = 1.4, 1.8, 2.2, 1.8, 0.8
serial_2mb = 2 * (attn + disp + gmm + comb) + engram_wait
dbo_2mb = 9.4  # uB0/uB1 Attn(0..2.8) + wait(0.4) + uB0/uB1 MoE(3.2..7.6) + hidden uB1 Comb(7.6..9.4)
speedup = serial_2mb / dbo_2mb
assert np.isclose(serial_2mb, 15.2) and speedup > 1.6
print(
    f"[10-synthesis] kv_bytes=(V2/3:{kv_v23_bf16}B, V3.2:{kv_v32_fp8}B, V4.1:{kv_v41_fp4}B), "
    f"serial_ms={serial_2mb:.1f}, dbo_ms={dbo_2mb:.1f}, speedup={speedup:.2f}x"
)
```

实测输出：

```text
[10-synthesis] kv_bytes=(V2/3:1152B, V3.2:576B, V4.1:288B), serial_ms=15.2, dbo_ms=9.4, speedup=1.62x
```

## 代价与边界：全链路耦合下的工程权衡

- **图捕获与微批切分必须严守静态形状**：`vllm/v1/worker/gpu/cudagraph_utils.py` 明确限制 DBO（`num_ubatches > 1`）只能跑在 `FULL` 静态图模式并禁止回落 `PIECEWISE`；一旦批内请求数不足以切出均衡微批，切分和事件同步开销就会反过来拖慢吞吐。
- **跨部件状态一致性校验不可省**：在 V4.1 同一层内并存 `CompressorStateCache`（循环缓冲）、`topk_indices_buffer`（跨层共享）、`EngramModelState`（双微批独立查表缓冲）和 `DSpark` 回滚槽位；昇腾侧也必须用 `ExternalEvent` 与 `valid_token_count` 守卫图内空跑卡，任何一环越界或脏内存都会沿 `4` 条 `mHC` 通道放大。
- **硬件假设与实测口径边界**：本系列文中引用的毫秒调度示例（`15.2 ms` vs `9.4 ms`）与硬件特性边界（如 SM100 `288 B` NVFP4 记录与 GB200 排序阈值、昇腾 A5 vs 910B INT8/MXFP8 降级）均对照 `vllm@bb23c0a8`、`FlashMLA@395cb3af`、`DeepEP@f6aa38fe` 与 `vllm-ascend@3649b8ff` 静态源码及公开技术报告核验，不同网络拓扑（NVLink vs HCCS vs RoCE）下的绝对加速比仍需以真机实测剖析为准。
