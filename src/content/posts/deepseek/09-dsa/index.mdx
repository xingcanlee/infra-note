NSA 有一步很漂亮：**选块的分数是从压缩分支白捡的**。但这也是它的约束——选择的粒度被绑定在压缩分支的块上，而且选得好不好取决于压缩表示的质量。

如果想要 **token 级**的精细选择呢？那就得对每个历史位置单独打分。于是矛盾出现了：

> 要挑出最相关的 $k$ 个位置，必须先给**全部** $L$ 个位置打分。打分本身就是 $O(L^2)$——我们绕了一圈又回到了原点。

DSA（DeepSeek Sparse Attention）的回答不是消除这个 $O(L^2)$，而是**让它的常数小到可以忽略**。读完你能回答：Lightning Indexer 便宜在哪三处、为什么稀疏作用在 latent 上、以及 indexer 是怎么被训练出来的。

## 先看一个例子

静态稀疏（窗口、选块）的形状只取决于位置。按内容打分的稀疏，形状**随输入变化**——同一个位置，换一句话就可能读完全不同的历史：

这就是动态稀疏的价值：它能挑到**真正相关**的远处位置，而不只是「最近的」或「开头的」。代价就是那个打分。

DSA 把这件事拆成了上下两条路——一条便宜的只管打分，一条昂贵的只算被选中的那些：

注意连接两条路的那条虚线标着「只选，不改变 latent 本身」——**indexer 的输出是一组下标，不是数值**。这一点下面会反复用到。

## 机制

### Lightning Indexer

对 query token $\mathbf h_t$ 和此前的 $\mathbf h_s$，index score 是（§2.1 式 (1)）：

$$
I_{t,s}=\sum_{j=1}^{H^{I}} w_{t,j}^{I}\cdot \mathrm{ReLU}\big(\mathbf{q}^{I}_{t,j}\cdot \mathbf{k}^{I}_{s}\big)
$$

$H^I$ 是 indexer 的 head 数，$\mathbf q^I_{t,j}$、$w^I_{t,j}$ 由当前 token 导出，$\mathbf k^I_s$ 由历史 token 导出。

形式上它就是一个小型注意力打分。便宜在三处：

| 便宜点          | 做法                                   | 为什么                                           |
| --------------- | -------------------------------------- | ------------------------------------------------ |
| **head 少**     | $H^I$ 远小于主注意力的 head 数         | 打分只需判断「相不相关」，不需要表达力            |
| **ReLU 代替 exp** | 用 $\mathrm{ReLU}$ 而不是指数/softmax | 论文明确说是**为了吞吐量**：ReLU 比 exp 便宜得多 |
| **FP8**         | indexer 可以用 FP8 实现                | 打分只用来排序，精度要求远低于主注意力           |

注意第三点背后的道理：**打分的结果只参与「选谁」这个离散决策，不进入最终输出**。排序对数值误差的容忍度比加权求和高得多，所以可以放心降精度。这和第 13 篇 MoE 里「bias 只影响选择、不进入权重」是同一种思路——**把不影响输出的部分做便宜**。

然后取 top-$k$，主注意力只在选中的条目上计算（§2.1 式 (2)）：

$$
\mathbf{u}_{t}=\mathrm{Attn}\Big(\mathbf{h}_t,\ \big\{\mathbf{c}_s \mid I_{t,s}\in\mathrm{Top\text{-}k}(I_{t,:})\big\}\Big)
$$

### 复杂度：降的是哪一项

| | 复杂度 | 常数 |
| --- | --- | --- |
| Indexer | $O(L^2)$（**没降**） | 很小：head 少、ReLU、FP8 |
| 主注意力 | $O(L^2)\rightarrow O(Lk)$ | 大：完整的 MLA |

论文的说法是：indexer 仍是 $O(L^2)$，但因为 head 数小且用 FP8，其计算量远小于 V3.1-Terminus 的 MLA（§2.3）。

**这是一笔明确的交易：用一个常数很小的 $O(L^2)$，换掉一个常数很大的 $O(L^2)$。** 不是渐近复杂度的胜利，是常数的胜利。理解这一点很重要——它意味着 DSA 的收益在序列足够长、且 indexer 实现足够优化时才成立。

$k$ 的取值是固定的 **2048**（§2.1.1 稀疏训练阶段），不随上下文长度变化。在 128K 上下文下这意味着每个 query 只读约 1.6% 的历史（这个比例是由论文配置推算的，不是论文直接报告的指标）。

### 为什么稀疏作用在 latent 上

DSA 是**在 MLA 之上**实例化的（§2.1，图 2）。回忆第 04–05 篇：MLA 缓存的是 latent $\mathbf c_s$，不是每个 head 的 K/V。DSA 选的正是这些 latent 条目。

而且论文在 kernel 层采用 MLA 的 **MQA mode**：每个 latent 在一个 query token 的**所有 query head 之间共享**（§2.1）。于是 top-$k$ 选择也是所有 head 共用一套。

这和第 08 篇 NSA 让 GQA 组内共享块索引是**同一个道理**：如果每个 head 各选各的，实际访存是所有 head 选择的并集，计算稀疏了而访存没有。稀疏注意力的收益主要是访存收益，所以「选择的粒度必须和 KV 共享的粒度对齐」。这条规律到这里已经出现第三次了（GQA → NSA → DSA），值得记住。

### indexer 是怎么训练出来的

indexer 要学会「预测主注意力会关注哪里」。论文分两阶段（§2.1.1）：

**阶段一：dense warm-up。** 保持密集注意力，**冻结模型其余参数，只训练 indexer**。目标分布 $p_{t,:}$ 由主注意力分数在所有 head 上求和、再沿序列做 L1 归一化得到；indexer 用 KL 散度去对齐它（式 (3)）：

$$
\mathcal{L}^{I}=\sum_{t}\mathbb{D}_{\mathrm{KL}}\big(p_{t,:}\,\|\,\mathrm{Softmax}(I_{t,:})\big)
$$

配置：learning rate $10^{-3}$，1000 步，每步 16 条 128K 序列，共 2.1B tokens。

**阶段二：sparse training。** 引入 top-$k$ 选择，优化全部参数。KL 只在被选中的集合 $\mathcal{S}_t$ 上计算（式 (4)）：

$$
\mathcal{L}^{I}=\sum_{t}\mathbb{D}_{\mathrm{KL}}\big(p_{t,\mathcal{S}_t}\,\|\,\mathrm{Softmax}(I_{t,\mathcal{S}_t})\big)
$$

配置：learning rate $7.3\times10^{-6}$，$k=2048$，15000 步，每步 480 条 128K 序列，共 943.7B tokens。

两个关键设计：

1. **indexer 的输入从计算图 detach**。indexer 只从 $\mathcal{L}^I$ 拿梯度，主模型只按语言建模损失优化。两个目标不互相干扰——否则主模型可能会为了「让 indexer 好学」而扭曲自己的注意力分布。
2. 整个流程从一个**已经扩展到 128K 的 V3.1-Terminus checkpoint** 继续训练，不是从头训。这和 NSA 的「原生可训练」是两条不同的路线：NSA 从预训练第一步就带着稀疏结构，DSA 是在稠密模型上改造。

严格说这不是标准的 teacher-student 蒸馏，论文也没这么称呼它；准确的描述是「把稠密主注意力的聚合分布作为 KL 目标」。

## 代码实现

> 完整可运行脚本见文章目录下的 `toy.py`。

```python
import numpy as np

def lightning_indexer(h_t, h_hist, W_q, W_k, W_w, H_I=4):
    """返回 h_t 对每个历史位置的 index score。head 少、ReLU、可用低精度。"""
    q = (h_t @ W_q).reshape(H_I, -1)          # (H_I, d_I) 少量小 head
    k = h_hist @ W_k                          # (L, d_I) 所有 head 共享一份 key
    w = h_t @ W_w                             # (H_I,) 每个 head 的标量权重
    return (w[:, None] * np.maximum(q @ k.T, 0)).sum(axis=0)   # ReLU，不是 exp

def dsa_select(scores, k):
    k = min(k, len(scores))
    return np.sort(np.argpartition(-scores, k - 1)[:k])
```

`toy.py` 做了三件事：

**① 衡量 indexer 挑得准不准。** 脚本按论文 §2.1.1 的 KL 目标真的把 indexer 训练了 400 步（梯度手写，因为 $\partial\,\mathbb{D}_{\mathrm{KL}}(p\|\mathrm{Softmax}(I))/\partial I = \mathrm{Softmax}(I) - p$，只有一行）。用「真实注意力权重的 top-k」当参考答案：

```
随机初始化的 indexer：  选中集合覆盖了 11.8% 的真实注意力质量
按 KL 目标训练之后：    选中集合覆盖了 35.5% 的真实注意力质量
（上限：直接取真实注意力 top-32 可覆盖 52.9%）
```

训练把覆盖率提高了 3 倍——这解释了为什么 indexer 必须训练，随机的 indexer 挑出来的基本是噪声。同时注意那个上限：即便直接用真实注意力权重挑 top-32（256 个位置里挑 32 个），也只能覆盖 52.9% 的注意力质量。**这正是第 08 篇提到的「top-20% 只覆盖约 70% 分数」那个长尾问题**，也是所有 top-k 稀疏方案共同的天花板。

**② 核对复杂度的交易。** 按乘法次数估算，indexer 与主注意力的对照：

```
L=   4096, k=2048：indexer 占总量 20.0%，主注意力省了 50.0%
L=  32768, k=2048：indexer 占总量 66.7%，主注意力省了 93.8%
L= 131072, k=2048：indexer 占总量 88.9%，主注意力省了 98.4%
```

注意最后一行：序列越长，**indexer 自己反而成了主要开销**，因为它是 $O(L^2)$ 而主注意力已经被压到 $O(Lk)$。这正是「常数的胜利，不是复杂度的胜利」的具体含义，也说明为什么 indexer 的实现必须极致优化。

**③ 固定 $k$ 的后果。** $k=2048$ 不随 $L$ 变：

```
L=   4096：读  50.0% 的历史
L=  32768：读   6.2% 的历史
L= 131072：读   1.6% 的历史
```

上下文越长，覆盖率越低。这是固定 token 预算的必然结果。

## 代价与边界

- **indexer 仍是 $O(L^2)$**。它只是常数小。在足够长的序列上，它会成为新的瓶颈（上面 ② 的第三行）。
- $k$ 固定为 2048，不随上下文长度调整。论文只给出 $k\ll L$，没有给出随 $L$ 变化的调度公式。长上下文下覆盖率必然下降。
- indexer 打分的质量决定一切：挑错了，主注意力再准也没用。而它的训练信号来自稠密注意力——这意味着它学到的是「稠密模型会关注哪里」，而稀疏训练阶段模型本身也在变。
- DSA 从稠密 checkpoint 改造而来，不是原生稀疏预训练。它与 NSA 不是同类方案的两个版本，而是两条不同的路线。
- **论文中未找到**：$H^I$ 和 $d^I$ 的具体数值、FP8 的格式与累加精度、indexer 相对主注意力的 FLOPs 或 latency 百分比。
- 论文 §2.3 图 3 给出 H800 集群上 prefill/decode 的 token 成本曲线（按 2 USD/GPU-hour 估算），但**正文没有给出一个明确的加速倍数或成本下降百分比**。从图上自己读数属于估读，本文不把它写成论文事实。上面 ② ③ 的数字是按公式算的乘法次数与比例，不是实测。

## 自测

1. DSA 把注意力的复杂度从 $O(L^2)$ 降到了 $O(Lk)$，为什么说它「没有解决 $O(L^2)$ 问题」？
2. Lightning Indexer 用 ReLU 而不是 exp、用 FP8 而不是 BF16。这两个选择背后是同一个理由，是什么？（提示：打分的结果参与了什么、没参与什么）
