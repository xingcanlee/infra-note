回头看[基础 01：硬件底座与 Roofline](../../foundations/01-hardware-and-roofline/)画出的 Roofline 屋顶图，自回归解码（Decode）最大的尴尬在于算力极度闲置。以 HBM 带宽 `3.35 TB/s`、FP8 算力 `1980 TFLOPS` 的单卡估算，每次吐出 `M = 1` 个词元时，整卡要把大约 `16 GB` 的激活权重从 HBM 完整搬进片上 SRAM 一次，算术强度只有区区 `2.0 FLOP/B`——离 `591 FLOP/B` 的计算屋脊差了将近三百倍。

既然权重已经耗费 `4.78 ms` 搬进了计算单元，如果让目标模型在同一次前向里**顺便多算几个候选词元（比如 `M = 5`）**，权重依然只读一次，算术强度翻到 `10.0 FLOP/B`，而总耗时却几乎纹丝不动。问题是，小模型或额外预测头一次吐出的草稿词元可能“猜错”，如果直接把错误概率混进输出，生成分布就会偏离原模型。

读完本章，你将掌握以下四个核心问题：

- **数学等价**：为什么“先用小模型草拟、再用大模型按比率拒绝并重采样”不会改变最终词元的任何一分概率质量。
- **因果串联 MTP**：DeepSeek-V3 为什么用 `enorm`、`hnorm`、`eh_proj` 把预测头串在因果链上，而不是做成互相独立的并行头。
- **DSpark 动态进化**：V4.1 的 DSpark（`arXiv:2607.05147`）如何用“3 层 SWA 并行主干 + 低秩马尔可夫链 + 置信度前缀调度”同时解决后缀坍塌与高并发算力浪费。
- **双引擎落地**：vLLM NVIDIA MRV2 与昇腾 `vllm-ascend` V2 如何通过统一填充长度、`topk` 索引复用与 TP 词表切分来守住设备图（CUDA Graph / ACLGraph）整图执行。

## 先看一个例子：3 步草稿加 1 步无损验证，目标分布为什么完全不变

假设词表只有 3 个词 `[A, B, C]`。当前位置上，昂贵的目标大模型算出的真实概率是 $p = [0.50,\, 0.20,\, 0.30]$，而便宜的草稿模型猜的概率是 $q = [0.40,\, 0.45,\, 0.15]$。可以看到，草稿把 `B` 高估了一倍多（`0.45 > 0.20`），却把 `A` 和 `C` 猜得偏低。

投机采样（Speculative Decoding）的核验规则非常直白：先从草稿分布 $x \sim q$ 抽出一个候选词，再掷一次均匀随机数 $r \sim U(0, 1)$，只要满足 $r \le \min(1,\, p(x)/q(x))$ 就当场接收；一旦拒绝，就丢掉该词并从**残差恢复分布** $p'(x) = \operatorname{norm}(\max(0,\, p(x) - q(x)))$ 里重新抽一个词替换掉它。

我们把这 3 个词的概率账一笔笔算清楚：

1. **草稿抽中 `A`（概率 0.40）或 `C`（概率 0.15）**：因为目标概率大于草稿概率（$p/q \ge 1$），接收阈值是 `1.0`，所以百分之百直接通过，分别给最终输出贡献 `A: 0.40` 与 `C: 0.15`。
2. **草稿抽中 `B`（概率 0.45）**：由于草稿把 `B` 高估了，只按比例 $p(B)/q(B) = 0.20 / 0.45 = 4/9$ 接收，于是 `B` 直接通过的净概率恰好等于 $0.45 \times 4/9 = 0.20$——正好对齐目标分布里 `B` 的份额！
3. **草稿抽中 `B` 但被拒绝（概率 $0.45 \times 5/9 = 0.25$）**：这多出来的 `0.25` 概率并没有凭空消失，而是流向残差分布 $p - q = [+0.10,\, -0.25,\, +0.15]$ 截断负值并归一化后的 $p' = [0.40,\, 0.00,\, 0.60]$，按缺口比例分别补给 `A`（$0.25 \times 0.40 = 0.10$）和 `C`（$0.25 \times 0.60 = 0.15$）。

把两条路径加总：最终吐出 `A` 的概率是 $0.40 + 0.10 = 0.50$，`B` 是 $0.20$，`C` 是 $0.15 + 0.15 = 0.30$。每一项都和目标模型独立采样**一模一样**。

## 数学保证与架构演进：从标准投机采样到因果串联 MTP

### 无损拒绝采样定理与期望加速比

把上面的单步直觉推广到连续草拟 $\gamma$ 步的标准投机采样定理[^specdec]：草稿模型自回归生成 $x_1, \dots, x_\gamma$ 及对应的分布 $q_1, \dots, q_\gamma$；目标模型在一次并行前向里同时给出 $p_1, \dots, p_{\gamma+1}$ 共 $\gamma+1$ 个位置的完整分布。

核验核按从左到右的顺序逐个检查：在位置 $i$，若 $r_i \le \min(1,\, p_i(x_i)/q_i(x_i))$ 则接收 $x_i$ 并继续下一位；在第一个拒绝位置 $n+1$（$n \le \gamma$）停止后续所有草稿，并从残差 $p'_{n+1}(x) = \operatorname{norm}(\max(0,\, p_{n+1}(x) - q_{n+1}(x)))$ 采样第 $n+1$ 个修正词元。若前 $\gamma$ 个词元全部接收，目标模型还白赚第 $\gamma+1$ 个位置的 logits，直接从 $p_{\gamma+1}(x)$ 采样出**奖励词元（Bonus Token）**——一次目标调用最少吐出 `1` 个、最多吐出 $\gamma + 1$ 个词元。

在各步期望接受率（即 $1 - E(D_{\text{LK}}(p,q))$）均为 $\alpha$、草稿单步时延占目标步时延比例为 $c = T(M_q)/T(M_p)$ 的独立近似下，单轮期望产出的词元数与端到端墙钟加速比分别满足：

$$
E[\text{tokens}] = \frac{1 - \alpha^{\gamma + 1}}{1 - \alpha}, \qquad \text{Speedup} = \frac{1 - \alpha^{\gamma + 1}}{(1 - \alpha)(\gamma c + 1)}
$$

其中：

- $\alpha \in (0, 1)$：单步草稿词元的平均接受率，等于 $\sum_x \min(p(x), q(x))$ 在上下文上的期望；$\alpha = 0.75, \gamma = 4$ 时每轮平均输出约 `3.05` 个词元。
- $\gamma$：每轮草拟步数（也是需要验证的最大前缀预算）。
- $c = T(M_q)/T(M_p)$：草稿单步前向时间与目标单步验证时间的比值，当草稿模型足够小或只附带几层轻量头时，$c$ 通常在 `0.03` 到 `0.08` 之间。

这个公式也埋下了高并发场景的隐患：它默认分母里的验证耗时永远是 `1`。当在线并发批大小 $B$ 升到上百，验证总词数 $B \cdot (1+\gamma)$ 跨过 Roofline 计算屋脊后，目标模型验证不再免费，固定用大 $\gamma$ 盲目验证低信心词元反而会挤垮整体吞吐。

### DeepSeek-V3 因果串联 MTP：训练密度与草稿连贯性

早期多词元预测常采用“并行独立头”思路（例如直接在最后一层隐状态上挂 4 个互不沟通的线性头）。这种结构看似一次就能吐出 4 个候选词，但位置 $t+2$ 的预测头根本不知道位置 $t+1$ 到底抽出了哪个词，联合分布的独立性假设会迅速拉低 $\alpha$。

DeepSeek-V3（`arXiv:2412.19437` §2.2）在设计多词元预测（MTP）时反其道而行之，把 $D$ 个预测模块做成了**因果串联链**[^dsv3]。在预测深度 $k$ 的第 $i$ 个位置上，MTP 模块把上一深度传来的隐状态 $\mathbf{h}_i^{k-1}$ 与“真实已知的下一步词嵌入” $\operatorname{Emb}(t_{i+k})$ 分别做 RMSNorm 后沿隐藏维拼接，再用矩阵 $M_k \in \mathbb{R}^{H \times 2H}$ 压回 $H$ 维，送入单层 Transformer 块：

$$
\mathbf{h}'^k_i = M_k \left[\operatorname{RMSNorm}(\mathbf{h}_i^{k-1});\, \operatorname{RMSNorm}(\operatorname{Emb}(t_{i+k}))\right], \qquad \mathbf{h}^k_{1:T-k} = \operatorname{TRM}_k(\mathbf{h}'^k_{1:T-k})
$$

随后通过**与主干完全共享权重的输出头** $\operatorname{OutHead}$ 投影出第 $i+k+1$ 个词元的概率分布，并按深度平均计算辅助训练损失 $\mathcal{L}_{\text{MTP}} = \frac{\lambda}{D}\sum_{k=1}^D \mathcal{L}_{\text{MTP}}^k$。

对照 vLLM 源码 `deepseek_mtp.py` 的 `DeepSeekMultiTokenPredictorLayer`，这条公式和代码严丝合缝：

- `hnorm` 与 `enorm` 对应双路 RMSNorm，`eh_proj` 正是无偏置的 $2H \to H$ 线性层，把拼接张量压回隐维度。
- 序列首位置 `positions == 0` 处不存在前序转移词元嵌入，代码第 120 行显式将 `inputs_embeds[positions == 0]` 清零后再拼接。
- `mtp_block` 是一层完整的 `DeepseekV2DecoderLayer`，因此每向后推演 1 步都要经过完整的自注意力并更新自己的草稿 KV Cache；`SharedHead` 则复用主干的最终归一化与词表权重，把每步新省下来的隐藏维参数留给主干吸收训练监督。

这种设计最初为预训练提供了更密集的梯度信号，推理时也能保留多步上下文依赖；但当系统想一次起草 $\gamma = 5$ 步甚至更多步时，因果串联 MTP 需要串行跑 $\gamma$ 遍重型块前向，$c \cdot \gamma$ 累加延迟又重新抬高了草稿开销。

## V4.1 进化：DSpark 半自回归起草与置信度自适应调度

为了既拿掉串联 MTP 的 $\gamma$ 倍前向延迟，又解决并行草稿在词间转移上的后缀坍塌，DeepSeek-V4 与 V4.1-Flash 引入了 **DSpark**（`arXiv:2607.05147`）[^dspark]。它没有推翻无损验证框，而是在**草稿结构**和**验证长度决策**两处动了大手术。

![DeepSeek-V3 因果串联 MTP 与 V4.1 DSpark 半自回归 + 轻量链式采样结构对比](./diagrams/13-mtp-dspark-arch.drawio '图 2：DeepSeek-V3 因果串联 MTP 与 V4.1 DSpark 半自回归 + 轻量链式采样结构对比')

### 1. 半自回归架构：1 次并行块前向 + 微秒级低秩马尔可夫链

DSpark 在 DeepSeek-V4/V4.1 上的落地形态精简而克制：它用 **3 层滑动窗口（SWA，$W = 128$）的 Transformer/MoE+mHC 模块**作为草稿主干，单轮固定草拟 $\gamma = 5$ 步（模型权重以 `mtp.{0,1,2}.*` 命名复用加载约定）。

与标准逐词生成不同，DSpark 把当前已知词元作为锚点（Anchor），后面拼上 $\gamma - 1$ 个占位 Mask 词元，构成长度为 $\gamma$ 的块输入，并把目标模型中间指定层隐状态的拼接归一化结果 $H_{\text{ctx}} = \operatorname{RMSNorm}(W_c[H^{(l_1)};\dots;H^{(l_m)}])$ 经 `context_wkv_proj` 注入草稿层 SWA 的 KV 缓存（源码 `_insert_context_kv`）。只需**一次并行前向**，草稿主干就同时吐出全部 $\gamma$ 个位置的基础 logits $U_1, \dots, U_\gamma$ 以及对应的隐特征 $h_1, \dots, h_\gamma$。

如果直接按 $U_k$ 各自独立采样，同样会撞上后缀退化墙。DSpark 的巧思在于后面挂了一个极轻量的**低秩马尔可夫头**（Markov Head，秩 $r = 256$）：

$$
L_k = U_k + W_1[x_{k-1}]\, W_2, \qquad W_1 \in \mathbb{R}^{V \times r},\; W_2 \in \mathbb{R}^{r \times V}
$$

第 $k$ 步首先算出上一步真正抽到的词 $x_{k-1}$，查表取出它的 $r$ 维向量 $W_1[x_{k-1}]$，只做一次微小向量矩阵乘就能修正整张词表的条件概率。主干计算全部被压进 1 步并行里完成，真正留在串行路径上的只有 `r = 256` 级别的查表与小矩阵乘，因此哪怕步长拉到 $\gamma = 5$，草稿侧时延增幅仍然微乎其微。

### 2. 置信度头与非预期因果前缀调度器

既然高并发下目标模型的验证成本不再恒定，那么“硬凑满 5 个草稿词元送去核验”就是种算力浪费——如果草稿自己都知道第 3 步开始概率发散，就不该让整批卡都陪它跑满 5 步。

DSpark 为每个草稿步挂上了一个两维投影置信度头 $c_k = \sigma(w^\top [h_k;\, W_1[x_{k-1}]])$，训练时直接用目标与草稿分布的软总变差重叠率 $c_k^* = 1 - \frac{1}{2}\|p_k^d - p_k^t\|_1$ 做二元交叉熵监督（联合权重衰减的 $\mathcal{L}_{\text{ce}}$ 与 $\mathcal{L}_{\text{tv}}$ 目标），并在训练后执行**顺序温度缩放（Sequential Temperature Scaling, STS）**校准，确保模型算出的累积存活概率 $a_{r,j} = \prod_{i \le j} c_{r,i}$ 精准逼近“第 $r$ 条请求前 $j$ 个词全被接收”的真实期望。

在在线服务调度上，设各请求保留的草稿前缀长度为 $\ell_r \in \{0, \dots, \gamma\}$，整批验证词数为 $B = \sum_r (1 + \ell_r)$，期望总产词量为 $\tau = \sum_r (1 + \sum_{j=1}^{\ell_r} a_{r,j})$。硬件感知前缀调度器的目标就是最大化实测系统吞吐率：

$$
\Theta = \tau \cdot \operatorname{SPS}(B)
$$

其中 $\operatorname{SPS}(B)$ 是实测标定的目标模型每步验证每秒步数（Steps Per Second）。这里藏着一个极易写错的数学陷阱——**非预期因果律（Non-Anticipating Causality）与阶梯图锯齿**：如果第 $k$ 步直接看当前这步自己选出来的总长度再决定是否提前中断（Early-Stopping），那么前面词的接收门限就会悄悄依赖于本批次未来算出的总体长，不仅破坏分布独立性，还会在 CUDA Graph/ZOS 的离散阶跃吞吐曲线上反复抖动。

生产实现（`2607.05147` §5.2 及 vLLM `adaptive_verification.py`）的解法极为干脆：利用**两步前的批容量滞后信号（`t-2` lag）**先定出本轮全批的总验证词元上限 $K$，形成严格的因果屏障；随后在固定配额 $K$ 下，把全批所有请求各步的 $a_{r,j}$ 放在一起排序截断（`_assign_draft_token_budget_kernel`），只把有限验证算力分给置信度最高的前 $K$ 个候选槽位。

在官方生产基准中（`2607.05147` §5.4），相比 MTP-1 基线，DSpark 让 V4-Flash 单用户生成速度提升 `60%–85%`（在 `80 tok/s/user` SLA 下总吞吐提高 `51%`，严苛的 `120 tok/s/user` SLA 下相对吞吐提升达 `661%`），也让 V4-Pro 单用户加速 `57%–78%`。而在 DeepSeek-V4.1 的训练全流程中（`arXiv:2609.19969` §2.4.3），DSpark 在主干预训练阶段被故意跳过，待主干定型后再冻结目标模型单独训练，并在后训练 RL/OPD 阶段保持联合更新（梯度不反传回主干）以始终贴合模型最新策略分布[^dsv41]。

## 生产运行时落地：vLLM MRV2 与昇腾 V2 源码对比

理解论文里的算术只是第一步；要把推测解码塞进高并发推理引擎，最头疼的是**如何不让动态接收长度把整图（CUDA Graph / ACLGraph）撕碎**。

![vLLM NVIDIA MRV2 与昇腾 V2 推测解码运行时对齐架构](./diagrams/13-specdec-runtime.drawio '图 3：vLLM NVIDIA MRV2 与 vLLM-Ascend V2 推测解码状态机与设备图适配')

### NVIDIA vLLM MRV2（`vllm@bb23c0a8`）

在 vLLM MRV2 架构重构后，早期的 `EagleProposer` 被拆解成结构清晰的 `vllm/v1/worker/gpu/spec_decode/` 子系统[^vllm]：

- **统一固定形状保整图（`TargetDependentARSpeculator`）**：虽然第 $r$ 条请求本轮可能在第 1 步就被拒绝，但为了让 `get_uniform_decode_token_count` 稳定命中 `CUDAGraphMode.FULL`，引擎在验证前后强制把每个并发请求都按最大规格 `1 + num_speculative_steps` 均匀填充并保留被拒绝槽位（`L142-147` 注释直接点明为了复用目标注意力元数据和槽位映射）。
- **跨步复用稀疏索引（`MTPSpeculator.index_share_for_mtp_iteration`）**：V3.2 与 V4.1 都采用了 CSA/DSA 稀疏注意力，如果串联 MTP 每步重跑一遍 Lightning Indexer 代价太高。因此源码规定第 `0` 步允许计算并紧凑化 top-k 索引（`set_skip_topk(False)` + `compact_topk_indices`），到了第 `1+` 步直接切换为 `set_skip_topk(True)` 复用前序检索结果。
- **TP 词表分片马尔可夫采样（`DSparkSpeculator`）**：`LMHead` 按张量并行（TP）切分词表时，直接串行跑马尔可夫链会引发每步都做全卡 `AllReduce` 的灾难。`DSparkSpeculator` 通过 `_sample_sequential_sharded` 先做 `all_to_all_vocab_shards` 把“按词表切分”重排为“按请求切分”，让每张卡在自己负责的那几条请求上拥有完整词表并本地跑完 $\gamma$ 步微秒级马尔可夫采样，最后一次 `all_gather` 拼回整批草稿。
- **拒绝采样内核（`RejectionSampler`）**：按 `gather_draft_sampled -> _verify_in_chunks -> _verify (rejection_sample) -> get_num_sampled_and_rejected` 四段推进，并配合 `AdaptiveVerificationManager` 在高并发开启自适应预算控制。

### 昇腾 vLLM-Ascend V2（`vllm-ascend@3649b8ff`）

昇腾后端在 `worker/v2/spec_decode/` 中直接通过多重继承（MRO）复用 MRV2 状态机骨架（如 `AscendMTPSpeculator` 继承 `(AscendTargetDependentARSpeculator, MTPSpeculator)`）[^ascend]，重点攻克 NPU 硬件流与集合通信的三个差异点：

- **ACLGraph 与 PCP 元数据防越界**：`AscendTargetDependentARSpeculator.propose` 用上下文管理器包住 `build_attn_metadata_wrapper` 和 `torch_gather_wrapper`，遇到预填充上下文并行（PCP）时通过 `_get_pcp_draft_prefill_metadata` 将草稿 Prefill 查询长度精确截断回真实槽位，避免静态 FULL 图对齐填充污染 Eager 侧草稿元数据。
- **LM Head TP 集合通信强对齐（`LmheadTPDraftSamplingMixin`）**：昇腾 CANN 图和自定义采样核要求 TP 通信前后批次维度严格一致。因此 `AscendDSparkSpeculator` 与 `AscendTargetDependentARSpeculator` 在跨步采样入口通过 `_lmhead_pad_size_context` 统一 pad/trim 边界，并由 P 节点调用 `initialize_local_context` 预先落盘本地上下文缓存。
- **拒绝采样算子边界差异（`rejection_sampler_utils.py`）**：受限于 NPU 内核当前实现约束，昇腾侧显式拦截了 `use_fp64`、批量分片 `draft_logits`、`fly_window_size` 滑动恢复及水印采样，同时拓展了 `use_entropy_verify` 以支持基于信息熵的变体核验。

## 动手运行：用 toy.py 验证无损分布与 Roofline 加速拐点

本节配套脚本 `toy.py`（纯 Python 标准库 + NumPy，`default_rng(42)`）共包含三组可复现实验：用 `10,000` 次单步拒绝采样验证实测分布与目标分布 $p$ 的总变差距离小于 `0.015`；模拟 $\gamma=4$ 步触发 Bonus 第 $K+1$ 词元的频率与理论产词量；以及用 Roofline 模型定量展示高并发下从内存受限跨越计算屋脊的临界拐点。

运行前只需执行如下命令：

```bash
uv run --with numpy python toy.py
```

脚本核心的 10,000 步拒绝采样核与 Roofline 拐点计算逻辑如下：

```python
def run_single_step_rejection_check(rng: np.random.Generator, n_trials: int = 10_000) -> None:
    vocab = ["A", "B", "C"]
    p = np.array([0.50, 0.20, 0.30])
    q = np.array([0.40, 0.45, 0.15])
    residual = np.maximum(0.0, p - q)
    residual /= residual.sum()

    counts = np.zeros(len(vocab), dtype=np.int64)
    for _ in range(n_trials):
        x = int(rng.choice(len(vocab), p=q))
        if rng.random() <= min(1.0, p[x] / q[x]):
            counts[x] += 1
        else:
            counts[int(rng.choice(len(vocab), p=residual))] += 1
```

## 代价与边界

多词元预测与动态推测解码把闲置的计算核心变成了实打实的加速比，但它同样引入了四条脆性工程边界：

- **接受率 $\alpha$ 对任务域与温度高度敏感**：当采样温度升高、开启高随机性创意写作，或遇到与草稿训练语料分布差异大的生僻代码库时，$\alpha$ 会迅速跌落到 `0.40` 以下。对照 `toy.py` 输出，$\alpha = 0.40$ 时理论加速只有 `1.26x`，一旦加上真实框架的图外调度和草稿通信开销，端到端反而可能慢于单步解码。
- **被拒绝词元的 KV 回滚与草稿污染风险**：目标模型并行验证 `1 + γ` 个槽位时已经把所有候选的 KV 写入或暂存进了分页槽位。尽管在 KV 物理页设计上只需要简单回退写入指针（`block_table` / 逻辑长度偏移），一旦遇到异步 Engram 预取（看回[07 条件记忆（Engram）](../07-engram/)）或上下文投影缓存未同步撤销，被拒绝后缀上的历史状态就会污染下一轮前缀。
- **大并发下 CUDA/ACL Graph 均匀填充的冗余开销**：为了让 `CUDAGraphMode.FULL` 捕捉静态形状，无论各请求通过置信度剪枝实际留了 `1` 个还是 `5` 个草稿词元，内核入口或槽位布局往往仍需按均匀步长或桶边界对齐。当批内不同请求的难度方差很大时，被填充占位却不产生有效新词的计算就会在计算屋脊上方产生实打实的算力损耗。
- **TP 切分下的集合通信放大**：DSpark 虽然把 3 层主干压缩到了 1 次前向，但如果 `LMHead` 采用词表切分 TP，多步连续采样若不做 `all_to_all_vocab_shards` 重排，单靠 `AllReduce` 同步每次词表 logits 就会被 NVLink/HCCS 延迟反噬，失去原本的微秒级低秩链优势。
