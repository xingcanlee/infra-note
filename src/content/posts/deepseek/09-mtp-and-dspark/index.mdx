自回归解码每吐出 $1$ 个 token，都要把整张大权重从 HBM 搬进计算单元一次。当批量较小或 KV 访问占主导时，算术强度远低于 GPU/NPU 的计算屋脊，绝大多数 Tensor Core / Cube 核心都在空转等数据。

推测解码（Speculative Decoding）把「先用廉价草稿模型连猜 $\gamma$ 步，再用大模型一次前向并行验证 $1+\gamma$ 个位置」当作解药：既然验证 $1$ 个 token 和验证 $8$ 个 token 的权重搬运量相同，多算的几个查询几乎不增加延迟，只要草稿猜中率够高，等效带宽开销就被摊薄了数倍。

本篇从理论到源码讲清三件事：无损拒绝采样如何做到「多步并发验证却不改目标分布一个比特」；草稿架构如何从 DeepSeek-V3 的串行因果 MTP 演进到 V4.1 DSpark 的单步 SWA 与低秩马尔可夫头；最后对照 `vLLM`（`bb23c0a8`）与 `vllm-ascend`（`3649b8ff`）看清图捕获、词表分片与异步截断的工程实现[^vllm-spec]。

## 无损拒绝采样：为什么速度翻倍却零精度损失

假设草稿模型顺次生成了候选序列 $(x_1, \dots, x_\gamma)$，对应的草稿分布为 $q(x)$，主干大模型一次性前向给出每个位置上的真实条件概率 $p(x)$。如果不做校正地直接按阈值接纳，输出分布就会偏向廉价草稿模型。

标准无损拒绝采样的核心规则只有三行，图 1 用具体的概率条与重采样流直观拆解了每一步的等价变换：

结合图 1，在每个候选位置依次抽取均匀随机数 $u \sim U(0, 1)$ 并按三步裁决：

1. **接受判定**：若 $u \le \min\!\big(1, p(x)/q(x)\big)$，则正式保留草稿词元 $x$ 并继续检验下一位置；否则立即在当前位**拒绝**并丢弃之后所有草稿后缀。
2. **残差分布重采样（First Reject）**：在第一个被拒绝的位置上，构造截断归一化残差分布 $p'(x) = \mathrm{norm}\!\big(\max(0,\, p(x) - q(x))\big)$，并从中精确抽回 $1$ 个合法词元替代原草稿。
3. **全接受奖励词元（Bonus Token）**：如果 $\gamma$ 个候选位置全部通过验证，大模型在末端位置 $\gamma+1$ 早已算出的 logits 还能白拿 $1$ 个额外采样词元，单步最多推进 $\gamma + 1$ 个 token。

### 数学等价证明：总输出概率恒等于目标分布

对词表里任意词元 $x$，最终在这一位输出 $x$ 的事件由「草稿选出 $x$ 且被接受」和「某次拒绝落入残差重采样并抽中 $x$」两互斥事件组成。先计算拒绝发生的总概率 $P(\text{reject})$：

$$
P(\text{reject}) = \sum_{y} q(y)\left(1 - \min\!\left(1, \frac{p(y)}{q(y)}\right)\right) = \sum_{y} \max\!\big(0,\, q(y) - p(y)\big)
$$

因为 $\sum_y p(y) = \sum_y q(y) = 1$，超出概率质量和欠缺概率质量必相等，即 $\sum_y \max(0, q(y)-p(y)) = \sum_y \max(0, p(y)-q(y)) = Z$，恰好等于残差分布的分母。于是最终落到任意 $x$ 的概率为：

$$
P_{\text{final}}(x) = q(x)\min\!\left(1, \frac{p(x)}{q(x)}\right) + P(\text{reject}) \cdot \frac{\max(0, p(x)-q(x))}{Z} = \min(p(x), q(x)) + \max(0, p(x)-q(x)) = p(x)
$$

这意味着无论草稿模型多么粗糙（即便某些分支上 $q(x)$ 严重偏离 $p(x)$），单步以及递推到整句的边缘与条件联合分布都严格等于主干大模型独立采样的结果，差别仅落在**期望接受长度**上。

## 从 DeepSeek-V3 因果 MTP 到 V4.1 DSpark

搞定无损验证之后，真正的工程瓶颈转移到了**草稿侧本身的延迟**：如果草稿模型自己每步都要跑一次串行层和全词表采样，推测预算会被草稿吃掉大半。图 2 对比了两代架构的时序演化：

### DeepSeek-V3 因果 MTP：串行轻量层复用共享头

在 `vllm/model_executor/models/deepseek_mtp.py`（`L48-175`）中[^vllm-spec]，`DeepSeekMultiTokenPredictorLayer` 把上一层主干输出隐状态与第 $k$ 步输入嵌入分别过 `RMSNorm`（`hnorm`、`enorm`），沿特征维拼接后经 `eh_proj` 压回 `2H -> H`：

- **因果传递**：合并特征再过 $1$ 个轻量级 `mtp_block`（含完整自注意力和 MoE/FFN）写回自己的草稿 KV，最后送入 `SharedHead`（`norm + ParallelLMHead`）采样第 $k$ 步草稿。
- **串行天花板**：当预测深度 $K=3$ 时，引擎仍需按步串行发起 $3$ 次 `mtp_block` 前向与 $3$ 次全词表投影采样；即便单层权重远小于主干，小批量下的核启动（kernel launch）与 `AllReduce` 延迟也会累积到不可忽视的量级（如图 2 上泳道所示）。

### V4.1 DSpark：单次 3 层 SWA + 低秩马尔可夫头与置信度裁剪

DeepSeek-V4.1-Flash（arXiv:2609.19969）[^v41-flash]用 **DSpark** 把「多步串行自回归」改造成了「**一次并行特征提取 + 微秒级低秩马尔可夫链**」，对照 `vllm_ascend/models/deepseek_v41/dspark.py`（`L1-310`）与 `vllm/model_executor/models/qwen3_dspark.py`（`L1-95`），核心包含四项协同设计：

1. **目标多层上下文压缩注入**：主干模型挑选若干代表层的隐状态拼接，通过 `main_proj` 和 `context_wkv_proj` 写入 DSpark 自己的 3 层滑动窗口注意力（SWA）KV 槽位，草稿主干一次前向并行输出未来 $\gamma$ 个位置的上下文特征，不再按步回流运行整层注意力。
2. **低秩马尔可夫条件修正头（`DSparkMarkovHead`）**：并行块虽能同时算出各未来位置的特征，却缺了「刚采出来的第 $k-1$ 个词对第 $k$ 个词的条件强约束」。DSpark 给每步基础 logits 叠加上一个极窄的低秩双线性项：

$$
\mathbf{z}_k = \mathbf{z}_k^{\text{base}} + \mathbf{W}_1[x_{k-1}]\, \mathbf{W}_2, \qquad \mathbf{W}_1 \in \mathbb{R}^{V \times r},\; \mathbf{W}_2 \in \mathbb{R}^{r \times V},\; r = 256
$$

3. **并行查表与极低串行成本**：查一行 `W_1[x_{k-1}]` 再乘以 `W_2` 只是一次 $[B, 256] \times [256, V]$ 矩阵乘，图 2 下泳道展示了这一结构如何把连续几步串行降为微秒级马尔可夫采样步。
4. **置信度头（`DSparkConfidenceHead`）与自适应截断**：每个位置额外预测单步接受置信度 $p_k$，在运行时累乘出序列存活概率 $\prod_{j=1}^k p_j$；`AdaptiveVerificationManager` 通过 Triton 二分检索核 `_assign_draft_token_budget_kernel`（`adaptive_verification.py:60-100`）按当前全局步配额砍掉低收益长尾，防止无效占位把验证批推过 Roofline 计算拐点[^vllm-adaptive]。

## PyTorch / NumPy 核心实现：无损拒绝采样与低秩马尔可夫链

下面这段自包含 NumPy 脚本把两件核心计算同时落地并做数值校验：一边跑 $50{,}000$ 次无损拒绝采样与残差重采样验证分布总变差（TV），一边跑 $r=256$ 低秩马尔可夫条件草稿链并断言输出形状。

```python
import numpy as np

rng = np.random.default_rng(9)
p = np.array([0.35, 0.25, 0.30, 0.10], dtype=np.float64)
q = np.array([0.20, 0.50, 0.20, 0.10], dtype=np.float64)
trials = 50000
counts = np.zeros(4, dtype=np.int64)
drafts = rng.choice(4, size=trials, p=q)
u = rng.random(trials)
res = np.maximum(0.0, p - q)
res_p = res / res.sum()
accept_mask = u <= np.minimum(1.0, p[drafts] / q[drafts])
for d_tok, acc in zip(drafts, accept_mask):
    if acc:
        counts[d_tok] += 1
    else:
        counts[rng.choice(4, p=res_p)] += 1
emp = counts / trials
tv = 0.5 * np.sum(np.abs(emp - p))
assert tv < 0.01

B, n_spec, V, r = 2, 5, 1024, 256
base_logits = rng.standard_normal((B, n_spec, V)).astype(np.float32)
w1 = rng.standard_normal((V, r)).astype(np.float32) * 0.05
w2 = rng.standard_normal((r, V)).astype(np.float32) * 0.05
prev = np.array([10, 42], dtype=np.int64)
drafted = np.zeros((B, n_spec), dtype=np.int64)
for i in range(n_spec):
    bias_i = w1[prev] @ w2
    logits_i = base_logits[:, i] + bias_i
    prev = np.argmax(logits_i, axis=-1)
    drafted[:, i] = prev
assert drafted.shape == (B, n_spec)
print(
    f"[09-mtp-dspark] lossless_TV={tv:.5f}, accept_rate={accept_mask.mean():.4f}, "
    f"dspark_draft_shape={drafted.shape}"
)
```

实测输出：

```text
[09-mtp-dspark] lossless_TV=0.00374, accept_rate=0.7525, dspark_draft_shape=(2, 5)
```

尽管人为把第 $2$ 号词元的草稿概率放大到目标的两倍（`0.50` vs `0.25`），五万次采样后实测总变差仅为 `0.00374`（远低于 `0.01` 阈值），而单步接受率 `0.7525` 也严格对齐理论期望 $\sum_x \min(p, q) = 0.20 + 0.25 + 0.20 + 0.10 = 0.75$。

## 双硬件生产运行时：vLLM GPU vs vllm-ascend

把草稿循环真正塞进多卡张量并行（TP）与静态图捕获（CUDA Graph / ACLGraph）时，GPU 与昇腾 NPU 在运行时栈的设计上走出了明显分岔。图 3 展开了两套调度与采样堆栈：

![vLLM GPU 与 Ascend NPU Speculator 运行时栈对照](./diagrams/09-mtp-vllm-runtime.drawio '图 3：vLLM V1 GPU Speculator 与 vllm-ascend V2 混合扩展运行时栈对照')

对照图 3 与两仓源码，关键工程分岔集中在五个环节：

| 机制维度         | `vllm` GPU MRV2（`bb23c0a8`）                                                           | `vllm-ascend` V2（`3649b8ff`）                                                            |
| ---------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **草稿类层次**   | `MTPSpeculator` / `DSparkSpeculator`（继承 `DFlashSpeculator`）                         | `AscendMTPSpeculator` / `AscendDSparkSpeculator`（`worker/v2/spec_decode/`）              |
| **稀疏索引共享** | `MTPSpeculator.index_share_for_mtp_iteration` 在第 `1+` 步复用首步索引                  | 对 `DSA`/`SFA` 跳过步间解码元数据重写，走 `AscendTargetDependentARSpeculator`             |
| **多卡词表采样** | `DSparkSpeculator._sample_markov_chain` 调 `all_to_all_vocab_shards` 按请求分片本地采样 | `LmheadTPDraftSamplingMixin` 将草稿 logits 填充对齐到 `max_num_reqs * num_spec_steps`     |
| **动态预算截断** | `AdaptiveVerificationManager` + `_assign_draft_token_budget_kernel` 位转换二分定阈值    | `NPUModelRunner` 调用 `compact_batch` / `reallocate_drafts`（`model_runner.py:923`）      |
| **拒绝采样内核** | `rejection_sampler.py` 原生核支持 fp64 校验与批量分片草稿 logits                        | `rejection_sampler_utils.py` 禁用 `use_fp64`/水印，改用 `_probabilistic_rejection_kernel` |

### 源码里的关键适配细节

- **GPU 词表分片 `All-to-All`**：在 `vllm/v1/worker/gpu/spec_decode/dspark/speculator.py` 中[^vllm-spec]，`DSparkMarkovHead` 的 `w1` 与 `w2` 在各 TP rank 保持轻量复制或分片配合，`all_to_all_vocab_shards` 把原本按词表维度分散在各卡上的基础 logits 转置为「每张卡握有部分请求的完整词表」，从而让 $\gamma$ 步链式采样全程留在本卡高速缓存里完成，零卡间 `AllReduce`。
- **NPU 词表分片对齐**：`vllm_ascend` 的 `dspark/speculator.py`[^ascend-spec]将 `supports_batch_sharded_draft_logits` 设为 `False`，由 `LmheadTPDraftSamplingMixin` 对齐填充 `max_num_reqs * num_speculative_steps`，并在核内禁用 `use_fp64`、`fly_window_size > 0` 与水印。
- **动态验证与静态图兼容性**：只要开启 `AdaptiveVerificationManager`，各请求的验证步数就会随置信度动态波动。因此 `NPUModelRunner`（`model_runner.py:916-938`）在启用动态裁剪时会避开固定全图或走 `compact_batch` 紧缩输入；GPU 侧则由 `resolve_adaptive_cudagraph_mode` 切换路由。

## 代价与边界

- **接受率崩溃的负加速区**：无损拒绝采样虽然保证精度零损失，但收益完全系于单步接受率 $\alpha$；在高随机性采样或未见长代码库场景下，若 $\alpha$ 跌落过低，额外草稿前向与多槽位验证不仅不能抵消开销，反而会把步长拉慢。
- **被拒绝后缀的辅助状态回滚**：主干验证 `1 + gamma` 槽位时，分页 KV 缓存只需回退写入指针即可逻辑作废尾槽；但诸如 DSpark 的 `context_wkv_proj` 状态、SWA 滑窗边界或前置的 Engram 异步预取缓存，若未跟着回滚就会污染下一轮前缀。
- **全图填充与分片对齐的算力浪费**：当同批请求里少数简单请求连猜 `5` 步、多数困难请求只留 `1` 步时，静态对齐填充或未满配额位仍会挤占计算资源。

至此，DeepSeek 系列最核心的每一块拼图——从 MLA 压缩、稀疏索引、DeepSeekMoE、Engram、mHC 到 MTP 与 DSpark——都已经逐个拆净。最后一篇 [10 串珠成链：从 DeepSeek-V2 到 V4.1 的单步全链路与双硬件全景](../10-architecture-synthesis/)将把这些部件合入同一条 decode 时间线与 Dual-Microbatch 集群流水线。
