上一篇搭好了坐标系：密度、单步代价上限、可达范围。这一篇用最简单的机制把三者之间的拉扯完整走一遍。

滑动窗口（Sliding Window Attention）的规则一句话说完：**只读最近 $W$ 个位置**。它简单到可以手写，却是后面所有多分支机制的底座——NSA、CSA 里都有一条窗口分支。读完你能回答：窗口为什么能让每步代价封顶、它丢了什么、为什么几乎没有模型敢单独用它。

## 先看一个例子

$W=2$，位置 3 只能读 {2, 3}：

/>

读取集合是

$$
\mathcal{S}_t = \{\,s : \max(0,\,t-W+1) \le s \le t\,\}
$$

$W=4$、$t=8$ 时就是 $\{5,6,7,8\}$。注意这是**逻辑位置**的集合，和它在显存里存在哪个槽位是两件事（下文会说）。

## 它改变了什么

和因果注意力对比，三个指标全变了：

|              | 因果               | 滑动窗口 $W$             |
| ------------ | ------------------ | ------------------------ |
| 单步读取量   | $t+1$，随 $L$ 增长 | $\min(t+1, W)$，**封顶** |
| prefill 总量 | $O(L^2)$           | $O(LW)$，**对 $L$ 线性** |
| 缓存必须保留 | 全部 $L$ 行        | 理论上只要最近 $W$ 行    |
| 单层可达     | 位置 0             | 位置 $t-W+1$             |

第三行是容易被忽略但工程上最重要的一条：**窗口让缓存本身有了上限**。因果注意力的缓存必须留着全部历史，窗口注意力只要留 $W$ 行——这意味着显存占用不再随对话长度无限增长。第 02 篇那个「488 GiB」的问题，窗口是另一种解法（压的是 $L$，而不是每行的宽度）。

代价写在最后一行。

## 代价：可达范围

单层只能看到 $W$ 个位置，但多层叠加后信息可以逐层往前传：第 $t$ 位在第 1 层读到 $t-W+1$，而 $t-W+1$ 在上一层又读过更早的位置。所以**理论可达范围大约是 $(W-1)\times n_{\text{layers}}$**。

这常被当作「窗口够用」的理由。代入真实量级看看——$W=4$、61 层、序列 4096，看最后一个位置能倒推多远（第 06 篇的 `receptiveField`，用真实可达性而非公式估算）：

| 层数 | 最早可达位置 |
| ---- | ------------ |
| 1    | 4092         |
| 8    | 4071         |
| 32   | 3999         |
| 61   | **3912**     |

61 层只倒推了 184 个位置。**可达范围按层数线性增长，而上下文长度是独立变大的**——两者不在一个量级上，差距只会越拉越大。

而且这还是乐观估计：可达性只说明「信息有路径传过来」，不代表它真的传得过来。每一层的注意力权重都可能很小，多层相乘后远处的贡献会指数衰减。所以 $(W-1)\times n_{\text{layers}}$ 是**上界**。

## 补救一：前缀锚点

一个便宜且有效的修补：窗口之外，永远保留开头的几个位置。

指标的变化（$L=8$）：密度从 41.7% 升到 58.3%，单步代价从 2 升到 3，但**单层可达范围直接从位置 6 变成位置 0**。花很小的代价买到了「永远能看到开头」。

为什么偏偏是开头几个位置？这就是 attention sink 现象：模型会把大量注意力权重堆在序列最开始的若干 token 上，即使它们语义上无关紧要。一种解释是 softmax 强制每行权重和为 1——当当前位置其实「不需要关注任何历史」时，这些权重总得有地方去，于是流向了最早出现、对所有位置都可见的那几个 token，它们成了一个「泄洪口」。

直接后果：**把开头几个 token 从缓存里丢掉，困惑度会显著变差**，哪怕它们看起来毫无信息量。StreamingLLM 的做法正是保留少量 sink token 加一个滑动窗口，从而在不重训的情况下支持长流式输入。

## 工程细节：逻辑位置 vs 物理槽位

窗口注意力的缓存只需 $W$ 行，所以实现上通常用**环形缓存**：第 $t$ 个 token 写进槽位 $t \bmod W$，写满就覆盖最旧的。

这里有个经典 bug。$W=4$、$t=8$ 时逻辑窗口是 $[5,6,7,8]$，但它们在环形缓存里的槽位是 $[1,2,3,0]$——**槽位顺序和逻辑顺序不一致**。于是：

- 算 RoPE 要用**逻辑位置**（5,6,7,8），不是槽位编号；
- 做掩码、排序、归约也要按逻辑位置；
- 只有寻址才用槽位。

把槽位编号当成位置用，模型不会崩，只会悄悄变差——因为位置编码错了。读这类实现时，第一件事就是确认「position 和 slot 在哪里被分开」。

## 代码实现

> 完整可运行脚本见文章目录下的 `toy.py`。

```python
import numpy as np

def sliding_window_mask(L, W, n_sink=0):
    """逻辑位置上的读取集合。n_sink > 0 时额外保留开头几个位置。"""
    t = np.arange(L)[:, None]
    s = np.arange(L)[None, :]
    m = (s <= t) & (t - s < W)
    if n_sink:
        m |= (s <= t) & (s < n_sink)
    return m

class RingCache:
    """只保留最近 W 个位置的环形缓存。"""
    def __init__(self, W, dim):
        self.W, self.buf = W, np.zeros((W, dim))
        self.pos = np.full(W, -1)          # 每个槽位当前存的是哪个逻辑位置

    def append(self, t, kv):
        slot = t % self.W                   # 覆盖最旧的
        self.buf[slot], self.pos[slot] = kv, t

    def read(self):
        """返回 (逻辑位置, 内容)，并按逻辑位置排序——这一步最容易漏。"""
        live = self.pos >= 0
        pos, buf = self.pos[live], self.buf[live]
        order = np.argsort(pos)             # 槽位顺序 ≠ 逻辑顺序
        return pos[order], buf[order]

cache = RingCache(W=4, dim=2)
for t in range(9):
    cache.append(t, np.array([t, -t]))
pos, _ = cache.read()
print('逻辑窗口：', pos)                     # [5 6 7 8]
print('物理槽位：', [int(t) % 4 for t in pos])  # [1, 2, 3, 0]  ← 顺序不同
```

输出：

```
逻辑窗口： [5 6 7 8]
物理槽位： [1, 2, 3, 0]  ← 顺序不同
```

`toy.py` 里还验证了：窗口缓存的显存占用有上限（与 $L$ 无关），以及丢掉 sink token 会让注意力分布发生明显变化。

## 代价与边界

- 窗口把单步代价和缓存上限都解决了，代价是可达范围。它适合「局部性很强」的任务，不适合需要精确引用远处内容的任务（长文档问答、代码库检索）。
- 可达范围的 $(W-1)\times n_{\text{layers}}$ 是上界，实际有效范围更短，而且无法直接测量。
- 环形缓存只有在**所有层都用窗口**时才能真正省显存。如果模型里混用窗口层和全注意力层（这是常见做法），全注意力层仍然要留完整缓存。
- attention sink 是经验现象，上面的「泄洪口」解释是一种广为引用的说法，不是定论。
- 本篇所有数字来自掩码的精确计算与 toy 运行，不是本机性能实测。

## 自测

1. 窗口 $W$ 让单步代价封顶。它同时解决了「缓存随 $L$ 增长」的问题吗？在什么前提下才算解决？
2. $W=512$、61 层。理论可达范围是多少？对 1M token 的上下文够用吗？
3. 为什么逻辑位置和环形槽位必须分开？如果用槽位编号算 RoPE，会发生什么（模型会报错吗）？
4. 加 1 个 sink 位置让单层可达范围从 $t-W+1$ 变成 0，代价只是每行多读 1 个。既然这么划算，为什么不多加几十个？
5. 动手：在 `toy.py` 里把 `n_sink` 从 0 改到 4，看注意力分布怎么变，并用第 06 篇的三个指标量化这笔交易。
