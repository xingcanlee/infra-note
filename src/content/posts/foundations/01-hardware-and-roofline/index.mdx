大模型推理在部署到加速卡上时，数据在片外高带宽显存（HBM）、片上暂存器与计算单元之间的往返搬运主导着实际延迟和吞吐。这一物理约束直接造成了推理两阶段的性能分化：一次输入整段提示词的 Prefill（预填充）能够把矩阵算力单元跑满，而每次只推进 1 个新 token 的 Decode（解码）几乎全程受制于显存搬运权重。

要看清后续的注意力融合、缓存压缩与低比特量化各自在解决什么问题，必须先把单层前向的数据形状、算力消耗和片上执行路径对齐到硬件账本上。

## 单层解码器前向张量剖面

在写出通用公式之前，先设定一个便于对齐尺寸的小批张量剖面 `[B=2, S=4, D=8]`：即同时处理 $B = 2$ 条请求、每条长度 $S = 4$ 个 token、隐藏特征维度 $D = 8$（整批共计 8 个 token）。注意力侧采用 2:1 分组查询结构，即每 2 个查询头共享 1 组键值头，因此键与值投影输出的总宽度减半为 $D_{kv} = 4$；前馈网络则采用 SwiGLU 门控结构，中间宽度扩至 $D_{\text{ff}} = 16$。图 1 展示了这批张量经过单层解码器五道工序时的形状变换、算子属性与字节流量分布。

![解码器单层前向张量流转与算力字节账本：注意力子层（RMSNorm、2:1 GQA 与残差）、SwiGLU 前馈子层及 BF16 流量汇总](./diagrams/01-forward-pass-flow.drawio '图 1：解码器单层前向张量形状、算子分类与字节流量分布（[B=2, S=4, D=8]）')

顺着图 1 标出的五个阶段，现代 Transformer（如 Llama、Qwen 与 DeepSeek 系列）的每层计算由以下五道工序串联而成。

第一阶段是进入注意力前的均方根归一化（RMSNorm）。深层网络经过多次残差累加后，隐藏向量幅值容易逐层漂移；为了在只做比例缩放而不减去均值的前提下稳住数值尺度，我们先统计向量各分量的均方根 $\text{rms}(x)$，再与可学习缩放向量 $\gamma$ 逐维相乘。为了便于口算，这里截取单个 token 隐藏向量的前 4 维 $x = [2.0, -1.0, 2.0, 0.0]$ 进行演示：

$$
\text{rms}(x) = \sqrt{\frac{1}{d}\sum_{i=1}^{d} x_i^2 + \varepsilon} = \sqrt{\frac{2^2 + (-1)^2 + 2^2 + 0^2}{4} + 10^{-6}} \approx 1.5000
$$

取全 1 缩放权重 $\gamma = [1, 1, 1, 1]$，归一化输出为 $\hat{x} = x / 1.5 \approx [1.3333,\ -0.6667,\ 1.3333,\ 0.0]$。若把输入 $x$ 整体放大 1000 倍，$\hat{x}$ 依然保持完全不变，这种尺度不变性为随后的矩阵乘法提供了稳定的输入分布。在 `[B=2, S=4, D=8]` 的 8-token 剖面上，第一阶段仅有约 192 次标量运算，读写代价却覆盖整份激活张量。

第二阶段是 QKV 线性投影。一般而言，形状为 $(M, K)$ 与 $(K, N)$ 的通用矩阵乘法（GEMM）每算出一个输出元素都要做 $K$ 次乘加（每次乘加计为 2 次浮点运算），因此总浮点运算量固定为 $2MNK$。在 `[B=2, S=4, D=8]` 剖面上，批大小与序列长度合并为行数 $M = B \times S = 8$，输入宽度 $K = D = 8$；归一化后的 $\hat{X}$ 同时乘以 $W_Q$、$W_K$、$W_V$ 三个权重矩阵，输出宽度合计 $N = 8 + 4 + 4 = 16$（得到 $Q$ `[2, 4, 8]` 与半宽 $K, V$ `[2, 4, 4]`），于是仅 QKV 线性投影就产生 $2 \times 8 \times 8 \times 16 = 2{,}048$ FLOPs。

第三阶段是因果自注意力与首次残差合流。$Q$ 与历史 $K, V$ 交换上下文后，再乘以输出投影矩阵 $W_O$ 映回 `[2, 4, 8]`，最后与入口残差 $X$ 相加得到中间状态 $X_{\text{mid}}$（注意力内部交互细节将在下一章单独展开）。在这一阶段，注意力点积与输出投影各自贡献 1,024 FLOPs，合计同样是 2,048 FLOPs。

第四阶段是第二层归一化与 SwiGLU 门控前馈网络（FFN）。不同于早期 Transformer 先升维再降维的两矩阵结构，现代大模型把升维拆成门控（Gate）和数值（Up）两条并行矩阵分支，在图 1 中把特征宽度从 8 扩充到 $D_{\text{ff}} = 16$：

$$
g = \text{SiLU}(\hat{x}_{\text{mid}} W_{\text{gate}}), \qquad u = \hat{x}_{\text{mid}} W_{\text{up}}, \qquad h = g \odot u \in \mathbb{R}^{D_{\text{ff}}}
$$

其中 $\text{SiLU}(z) = z \cdot \sigma(z)$ 是平滑门控激活函数，$g \odot u$ 表示两路中间向量逐元素相乘，随后 Down 矩阵 $W_{\text{down}}$ 把宽度压回 $D = 8$。因为多了一个升维权重，若要与经典两矩阵 $4d$ 扩展（参数量 $2 \cdot d \cdot 4d = 8d^2$）维持相当的参数预算，工程上常取 $d_{\text{ff}} \approx \frac{8}{3}d$ 并对齐硬件块粒度（例如 $d=4096$ 时取 $d_{\text{ff}}=11008$，参数总量约为经典结构的 1.008 倍）。回到 `[2, 4, 8]` 剖面，Gate、Up、Down 三个矩阵一共贡献 $3 \times (2 \times 8 \times 8 \times 16) = 6{,}144$ FLOPs，占全层 10,240 次矩阵乘法运算的 60%。

第五阶段则是将前馈网络输出与 $X_{\text{mid}}$ 执行第二次逐元素残差相加，得到单层输出 $Y$ `[2, 4, 8]`；全模型堆叠完所有解码器层后，末层出口再由词表投影（LM Head）映射为词表概率分布。

从硬件执行特征来看，这五道工序可以清晰划成两类截然不同的计算负载：QKV、O、Gate、Up、Down 与 LM Head 属于高密度规则矩阵乘（GEMM），占据了全层 95% 以上的浮点运算量，天然契合专攻矩阵乘累加的硬件单元；而 RMSNorm、SiLU、$g \odot u$ 与残差相加属于向量归约与逐元素算子，每个数只做几次乘加或指数运算却要读写整份激活张量，运行耗时几乎完全受限于片外显存或片上缓存的搬运带宽。在 vLLM 代码库中，`RMSNorm` 与 `SiluAndMul` 均继承自统一抽象 `CustomOp`[^vllm-customop]，由运行时依据设备平台分派给 CUDA Kernel 或 OOT 插件后端的专用算子[^vllm-norms]。

## NVIDIA GPU SM 与昇腾 DaVinci AI Core 微架构

同样的矩阵乘与向量归约交给 NVIDIA GPU 和华为昇腾 NPU 执行时，面对的是两套设计哲学完全不同的硅片。图 2 并排展示了 GPU 流式多处理器（SM）与昇腾达芬奇核心（DaVinci AI Core）的计算单元分工与片上存储通路。

### NVIDIA GPU SM 的缓存协同与张量加速

一颗现代 NVIDIA GPU 由数十至上百个流式多处理器（SM）组成，所有标量、向量与矩阵操作都在单指令多线程（SIMT）线程束（Warp）调度下协同推进。面向推理负载，矩阵乘核心由专用的 **Tensor Core** 承担——Ampere 架构采用线程束级同步矩阵指令 `MMA`，Hopper 架构进一步演化出异步线程束组指令 `WGMMA`，单周期即可吞下整片小块稠密矩阵乘累加。`RMSNorm` 中的平方根倒数、`SiLU` 中的指数函数、地址偏移计算以及注意力里的换行归一化，则交给通用 **CUDA Core** 与特殊函数单元 **MUFU** 完成。

在片上存储组织上，GPU 兼顾了显式共享与硬件透明缓存两条路线：每个线程独享高速寄存器组（Register File），同一线程块内的线程通过片上共享内存（SMEM）交换分块中间结果，而硬件自动管理的 L1 与 L2 缓存会透明截留高频访问地址，降低了 Kernel 开发者的显式搬运负担。从 Hopper 架构开始，专用异步引擎 **TMA（Tensor Memory Accelerator）** 可以依据多维张量描述符直接将片外 HBM 数据块异步拉入 `SMEM`；在内存排布上，PyTorch 与 CUDA 算子普遍采用行主序 `ND` 布局，只需保证 16 字节地址对齐就能高效利用连续访存合并。

### 华为昇腾 AI Core 的解耦流水与分形排布

与 GPU 由硬件 Cache 兜底的统一线程束模型不同，华为昇腾（包括 910B/A2、910C/A3 与新一代芯片）采用结构化的 **DaVinci AI Core**，在微架构物理层面把计算拆成三条独立的异步执行流水线。**Cube Unit** 是专攻半精度及量化矩阵乘的脉动阵列，单拍吞吐固定规格为 $16 \times 16 \times 16$ 的分形块；**Vector Unit** 负责 `RMSNorm`、`SiLU`、Softmax 等向量与超越函数运算；**Scalar Unit** 则扮演核内控制器，解码标量循环与同步标志，向 Cube、Vector 与数据搬运引擎异步派发指令。

由于片上存储不由硬件透明 Cache 自动接管，昇腾算子必须由软件显式编排数据迁徙路径。面向 Cube 的数据需通过异步 DMA 引擎 `MTE2` 从片外 HBM 搬入片上 **L1 Buffer**，再由 `MTE1` 切分送入矩阵乘专属缓冲 **L0A / L0B**，乘加累加和驻留在 **L0C**，最终经 `MTE3` 写回片外；而 Vector 单元的输入、输出与中间变量几乎全部驻留在 **UB（Unified Buffer）** 中[^ascend-ub]。在 910B 与 910C 上，单核 `UB` 容量默认为 192 KB（310P 为 128 KB）[^ascend-ub]，一旦融合算子同时存活过多 FP32 中间张量就会触发容量溢出。由于 `MTE2`、`Cube`、`Vector` 与 `MTE3` 各自拥有独立队列，精细调度的 Kernel 可以让 Cube 计算当前分块的同时，Vector 处理上一块的激活、MTE2 预取下一块权重，即 **CV 流水线重叠**[^ascend-prefill]。

正因为 Cube 单元以 $16 \times 16$ 为固定突发读取粒度，若权重沿普通行主序 `ND` 存放，跨行读取内维时每步都会产生非连续跨距搬运。为此，昇腾框架习惯在模型权重加载期一次性把 `ND` 格式重排为内部 `FRACTAL_NZ` 分形排布（非 16 倍数的矩阵维度向 16 补零对齐）[^ascend-nz]，让每次 16×16 子块都能以连续地址突发送进 L1 与 L0 缓冲。

| 硬件维度     | NVIDIA GPU SM            | 昇腾 DaVinci AI Core      | 工程影响                |
| :----------- | :----------------------- | :------------------------ | :---------------------- |
| 矩阵算力单元 | Tensor Core（MMA/WGMMA） | Cube（16×16×16 分形块）   | 维度须对齐 16B 或 16 块 |
| 向量与非线性 | CUDA Core + MUFU         | 独立 Vector 流水线        | 需关注 Cube/Vector 重叠 |
| 发射控制模型 | SIMT Warp 调度           | Scalar 核派发异步队列     | 依赖图捕获减少发射间隙  |
| 片上存储管理 | 寄存器 + SMEM + 硬件缓存 | 显式 L1/L0 与 192 KB UB   | 算子须严控 UB 驻留张量  |
| 异步搬运引擎 | Hopper+ TMA 多维拷贝     | MTE1 / MTE2 / MTE3 三通道 | 需双缓冲掩盖 HBM 延时   |
| 典型权重排布 | 通用行主序 ND 布局       | 加载期重排为 FRACTAL_NZ   | 须匹配设备加载转换      |

## Roofline 模型与两阶段瓶颈分化

把算子的浮点运算次数与片外显存读写字节数做比值，就得到了衡量硬件瓶颈的通用标尺——**算术强度（Arithmetic Intensity）**：

$$
I = \frac{\text{FLOPs}}{\text{Bytes}} \quad (\text{单位：FLOPs / Byte})
$$

对于任意加速卡，实际计算吞吐同时受两道物理上限约束：峰值矩阵算力 $P_{\text{peak}}$（TFLOPS）与显存读写带宽 $BW_{\text{HBM}}$（TB/s）。两者相交处的横坐标称作**拐点算术强度（Ridge Point）**：$I^* = P_{\text{peak}} / BW_{\text{HBM}}$。算子的理论吞吐上限由两道上限的较小值决定：

$$
P_{\text{attained}} = \min\!\left(P_{\text{peak}},\ I \cdot BW_{\text{HBM}}\right)
$$

把这条关系代回大模型最核心的 BF16 线性层（每个元素占 2 字节）：输入激活形状 $(M, K)$、权重 $(K, N)$、输出 $(M, N)$，总运算量为 $2MNK$，而从 HBM 读取权重、读取输入并写回输出的总访存量至少为 $2(KN + MK + MN)$ 字节。当并发 token 数远小于矩阵隐藏维（$M \ll K, N$）时，权重体量主导访存，算术强度直接化简为批大小本身：

$$
I = \frac{2MNK}{2(KN + MK + MN)} \approx \frac{2MNK}{2KN} = M
$$

这意味着单并发自回归解码（$M = 1$）的算术强度只有约 $1\text{ FLOP/B}$：每从显存搬来 2 字节权重，核心只做 2 次乘加就丢弃。以 FlashMLA 技术报告校准的 NVIDIA H800 SXM5（BF16 峰值 990 TFLOPS、HBM 带宽 3.35 TB/s，拐点 $I^* \approx 295.5\text{ FLOP/B}$）[^flashmla-doc] 为标尺，线性层必须积累大约 300 个并发 token 才能跨过带宽斜坡进入算力平台期。图 3 在对数坐标系上对照了 H800 与昇腾示例剖面（320 TFLOPS、1.60 TB/s，拐点 $I^* = 200\text{ FLOP/B}$）在同一套 $d = 4096,\,d_{\text{ff}} = 11008$ SwiGLU FFN（三矩阵 BF16 权重合计 258 MiB）下的性能轨迹，以及昇腾 Cube 与 Vector 流水线的重叠效果。

沿着图 3 的三个工况向右移动，可以清楚看到推理系统的吞吐瓶颈如何迁移。当处于单并发 Decode（$M = 1$）时，系统必须把全部 258 MiB 权重完整搬入核心才能吐出 1 个 token，算术强度停在 1.00 FLOP/B，H800 的有效算力被带宽锁在 3.35 TFLOPS（仅占峰值的 0.3%），昇腾示例剖面也只有 1.60 TFLOPS（0.5%），超过 99% 的时间计算单元都在空等 HBM 送数。当批大小扩大到 $M = 64$ 时，同一份权重被 64 个 token 摊分，算术强度上升到 62.86 FLOP/B（H800 达到 210.57 TFLOPS，昇腾剖面达到 100.57 TFLOPS），但依然位于两道拐点左侧的带宽斜坡上。进入长序列 Prefill（如 $M = 4096$）后，算术强度跃升至 1893.85 FLOP/B，计算跨过双硬件拐点达到算力天花板；此时在昇腾 AI Core 上启用异步 CV 双流水重叠[^ascend-prefill]，还能把 Vector 侧的归一化与门控激活延迟掩蔽在下一块 Cube 矩阵乘背后，在重叠区间压缩至 1.50 倍提速。

实际部署时，纸面带宽上限还受算子发射粒度制约：3.35 TB/s 假定的是连续大块读写，如果张量切得过碎或 Python 逐算子发射留下微秒级空闲，有效带宽会明显下滑，这也是 GPU 与昇腾都在解码关键路径上重度启用 `CUDA Graph` 与 `ACL Graph` 来固化整图发射序列的原因。

## NumPy 验证与双硬件设备分发

下面的自包含 NumPy 脚本同时复核图 1 的 `[B=2, S=4, D=8]` 单层张量前向形状，以及图 3 中 $d = 4096,\,d_{\text{ff}} = 11008$ SwiGLU 线性层在 $M = 1, 64, 4096$ 下的算术强度与 Roofline 上限（本地可通过 `uv run --with numpy python` 直接执行）：

```python
import numpy as np

rng = np.random.default_rng(7)
B, S, D, D_kv, D_ff = 2, 4, 8, 4, 16
X = rng.normal(0.0, 1.0, (B, S, D))
X_norm = X / np.sqrt(np.mean(X**2, axis=-1, keepdims=True) + 1e-6)
Q = X_norm @ rng.normal(0.0, 0.2, (D, D))
K = X_norm @ rng.normal(0.0, 0.2, (D, D_kv))
V = X_norm @ rng.normal(0.0, 0.2, (D, D_kv))
W_gate, W_up = rng.normal(0.0, 0.2, (D, D_ff)), rng.normal(0.0, 0.2, (D, D_ff))
W_down = rng.normal(0.0, 0.2, (D_ff, D))
gate = X_norm @ W_gate
silu_gate = gate / (1.0 + np.exp(-gate))
Y = X + (silu_gate * (X_norm @ W_up)) @ W_down
assert Q.shape == (2, 4, 8) and K.shape == (2, 4, 4) and Y.shape == (2, 4, 8)

wt_bytes = 3 * 4096 * 11008 * 2
for M in (1, 64, 4096):
    flops = 2 * M * 3 * 4096 * 11008
    bytes_io = wt_bytes + M * (4 * 4096 + 2 * 11008) * 2
    ai = flops / bytes_io
    print(f"M={M:4d}: AI={ai:7.2f} FLOP/B | H800={min(990.0, ai * 3.35):6.2f} TF | 910B={min(320.0, ai * 1.60):6.2f} TF")
```

脚本运行输出如下，算术强度与各工况算力上限和图 3 完全一致：

```text
M=   1: AI=   1.00 FLOP/B | H800=  3.35 TF | 910B=  1.60 TF
M=  64: AI=  62.86 FLOP/B | H800=210.57 TF | 910B=100.57 TF
M=4096: AI=1893.85 FLOP/B | H800=990.00 TF | 910B=320.00 TF
```

把同一套模型前向部署到不同厂商加速卡时，推理引擎依赖 PyTorch 的外置设备分发机制完成无侵入路由。PyTorch 原生内置了 `CUDA` 等分发键，同时为第三方硬件预留了统一的外置扩展键 `PrivateUse1`；在 `vllm-ascend` 中，`NPUPlatform` 将设备分发键设为 `"PrivateUse1"` 并声明为 Out-of-Tree（OOT）硬件插件后端（`PlatformEnum.OOT`）[^ascend-platform]，随后在初始化阶段把 `RMSNorm`、`SiluAndMul` 等核心算子覆写注册为昇腾实现[^ascend-reg][^ascend-ops]。上层模型前向无需判断硬件类型，只需调用 `CustomOp` 的统一入口即可自动切换执行路径[^vllm-customop][^vllm-norms]：

```python
# vllm/model_executor/custom_op.py:194-205 (vllm@bb23c0a8)
if current_platform.is_rocm():
    return self.forward_hip
elif current_platform.is_out_of_tree():
    return self.forward_oot
else:
    return self.forward_cuda

# vllm/model_executor/layers/activation.py:146-151 (NVIDIA GPU SwiGLU)
def forward_cuda(self, x: torch.Tensor) -> torch.Tensor:
    d = x.shape[-1] // 2
    out = torch.empty(x.shape[:-1] + (d,), dtype=x.dtype, device=x.device)
    self.op(out, x)  # torch.ops._C.silu_and_mul
    return out

# vllm_ascend/ops/activation.py:37-40 (vllm-ascend@3649b8ff, 昇腾 NPU SwiGLU)
class AscendSiluAndMul(SiluAndMul):
    def forward_oot(self, x: torch.Tensor) -> torch.Tensor:
        out = torch_npu.npu_swiglu(x)
        return out
```

两条硬件约束直接影响昇腾侧算子的落地方式：线性层权重必须在模型加载期重排为 `FRACTAL_NZ` 分形排布以匹配 Cube 的 16×16 突发读取[^ascend-nz]；编写融合算子时则必须将同时驻留的 FP32 中间变量控制在 192 KB `UB` 上限以内[^ascend-ub]。

到这里，线性层与前馈网络的权重搬运开销还与上下文长度无关；真正随着序列长度 $S$ 迅速放大的，是让前后 token 交换上下文信息的自注意力机制与键值缓存，这正是下一章 [02 自注意力与旋转位置编码（RoPE）：token 之间如何交换上下文](../02-attention-and-rope/) 要解决的问题。
