大模型推理在代码里看似只有一连串线性层与激活函数，但部署到真实加速卡上时，真正决定延迟与吞吐的往往不是公式复杂度，而是数据如何在 **HBM 显存、片上暂存器与计算单元** 之间往返搬运。如果看不清硬件到底在等数据还是在全力乘法，后续的注意力融合、KV 压缩与低比特量化全都会失去判断标准。

本章从零起点出发，先用张量剖面走通一次完整解码器层前向计算，算清每个算子的形状、FLOPs 与字节流量；再并排解剖 **NVIDIA GPU SM** 与 **华为昇腾 DaVinci AI Core** 两套微架构及软件分派链路；最后用 **Roofline 模型** 钉死全站最核心的认知：为什么 `Prefill` 是算力受限，而 `Decode` 每次吐 1 个词元会狠狠撞上带宽墙。

## 先看一个解码器层前向张量剖面

在写通用公式之前，先抓一个便于逐像素对齐的小批次张量：`[B=2, S=4, D=8]`（两个并发请求、每条 4 个词元、隐藏维 8），配合 2:1 GQA 投影（$D_{kv}=4$）和 SwiGLU 门控前馈（$D_{\text{ff}}=16$）。从单个词元的视角看，取一条 4 维向量 $x = [2.0, -1.0, 2.0, 0.0]$ 时，每一步经历的算子属性完全一致（见图 1 交互步骤演进）。

顺着图 1 的 5 个步骤拆解现代大模型（如 Llama、Qwen、DeepSeek）的逐层算子：

**第一步：RMSNorm 均方根归一化**。为了防止深层残差不断累加导致数值发散，先计算向量各分量的均方根 `rms(x)`，再做比例缩放而不减去均值：

$$
\text{rms}(x) = \sqrt{\frac{1}{d}\sum_{i=1}^{d} x_i^2 + \varepsilon} = \sqrt{\frac{2^2 + (-1)^2 + 2^2 + 0^2}{4} + 10^{-6}} \approx 1.5000
$$

取缩放权重 $\gamma = [1, 1, 1, 1]$，归一化结果为 $\hat{x} = x / 1.5 \approx [1.3333,\ -0.6667,\ 1.3333,\ 0.0]$。把 $x$ 整体放大 1000 倍，$\hat{x}$ 依然保持完全一致——这种尺度不变性让后续乘法拥有稳定的输入分布。

**第二步：QKV 线性投影与因果注意力**。图 1 第 2–3 步展示了 $\hat{X}$ 经过 $W_Q, W_K, W_V$ 投影为 $Q [2,4,8]$ 与半宽 $K, V [2,4,4]$，再做上下文交换后经 $W_O$ 加回残差 $X_{\text{mid}}$（这部分交互细节将在下一章单独拆开）。在 `[B=2, S=4, D=8]` 的 8-token 剖面上，仅 QKV 投影就贡献了 `2,048 FLOPs`，注意力点积与输出投影各占 `1,024 FLOPs`。

**第三步：SwiGLU 门控前馈网络（FFN）与残差**。经典 Transformer 只有升维和降维两个矩阵，现代大模型普遍把升维拆成 `Gate` 与 `Up` 两条并行分支，在图 1 中把宽度从 8 扩张到 16：

$$
g = \text{SiLU}(\hat{x} W_{\text{gate}}), \qquad u = \hat{x} W_{\text{up}}, \qquad h = g \odot u \in \mathbb{R}^{D_{\text{ff}}}
$$

其中 $\text{SiLU}(z) = z \cdot \sigma(z)$ 是平滑门控函数，$\odot$ 表示逐元素乘法。随后 `Down` 矩阵 $W_{\text{down}}$ 将维度压回 $D$，再执行残差相加。因为用了 3 个权重矩阵，若要与经典两矩阵 `4d` 扩展（参数量 $2 \cdot d \cdot 4d = 8d^2$）保持总参数持平，中间维度通常取 $\frac{8}{3}d$ 并对齐硬件块粒度（例如 $d=4096$ 时取 $d_{\text{ff}}=11008$，参数比约 `1.008x`）。最终出口的 `LM Head` 再将末层隐藏状态映射回词表 logits。

把算子分成**两类物理属性截然不同的工作**，你立刻就能摸到硬件优化的门道：

- **矩阵乘（GEMM）算子**（`QKV`、`O`、`Gate`、`Up`、`Down`、`LM Head`）：计算量大且高度规则，适合大吞吐矩阵引擎批处理。形状 $(M, K) \times (K, N)$ 的浮点运算量固定为 $2MNK$（每次乘加记 2 次 FLOPs），在图 1 的 8-token 剖面中 FFN 独占了 `6,144` 次（`60%`）运算。
- **逐元素与规约（Vector / Elementwise）算子**（`RMSNorm`、`SiLU`、`g ⊙ u`、`Residual +x`）：每个数只算几次加减或指数，却必须读写完整张量，几乎纯由内存带宽决定速度。

在 vLLM 代码库中，通用算子正对应上述分层抽象：`RMSNorm` 与 `SiluAndMul` 均继承自 `CustomOp`[^vllm-customop]，由运行时根据平台类型选择 CUDA 实现或插件提供的硬件核函数[^vllm-norms]。

## NVIDIA GPU SM 与昇腾 DaVinci AI Core 微架构对照

上面这两类完全不同性格的计算与访存工作，落在 **NVIDIA GPU** 和 **华为昇腾 NPU** 上时，面对的是两套设计哲学迥异的硬件硅片。图 2 将两者的核内数据通路与存储层级并排对照，看清这些组件才能真正理解后续算子优化的出发点。

### NVIDIA GPU SM：硬件缓存协同与 TMA 流式搬运

一颗 NVIDIA 现代 GPU 由数十至上百个 **流式多处理器（SM）** 组成。面向 Transformer 推理，单个 SM 内有四大角色各司其职（见图 2 左泳道）：

- **Tensor Core（矩阵引擎）**：专门处理小块稠密矩阵乘累加（Ampere 为同步 `MMA`，Hopper 引入异步 `WGMMA`），单个时钟周期能咽下整片矩阵乘。线性投影与注意力核心乘法全靠它打吞吐。
- **CUDA Core 与 MUFU（标量与特殊函数单元）**：负责向量加减、整数地址计算以及 `exp`、`rsqrt`、`sigmoid` 等非线性超越函数。`RMSNorm` 的平方根倒数与 `SiLU` 的指数运算都在这里完成。
- **Register File、Shared Memory（SMEM）与 L1/L2 Cache**：每个线程拥有高速寄存器组；同一线程块内线程通过片上 `SMEM` 共享分块数据；硬件管理的 `L1/L2 Cache` 会自动缓存高命中地址，降低编程心智负担。
- **TMA（Tensor Memory Accelerator）与通用 ND 布局**：从 Hopper 架构开始，专用异步拷贝引擎 TMA 可按多维描述符把 HBM 数据整块异步拉入 `SMEM`。PyTorch/CUDA 算子默认采用行主序 `ND` 布局，满足 16 字节对齐即可高效访存。

### 昇腾 DaVinci AI Core：显式三流水线、片上暂存区与 FRACTAL_NZ 分形排布

与 GPU 由硬件 Cache 兜底的 SIMT 线程束不同，华为昇腾（如 910B/A2、910C/A3 与新一代 A5）采用高度结构化的 **DaVinci AI Core**（见图 2 右泳道），把控制、矩阵与向量拆成三条**物理独立、异步并行**的执行流水线：

- **Cube Unit（16×16×16 矩阵核）**：面向半精度及量化输入，单次固定吞吐 $16 \times 16 \times 16$ 的分形矩阵乘，专注极致的矩阵算力密度。
- **Vector Unit 与 Scalar Unit（向量与标量核）**：`Vector Unit` 专吃 `RMSNorm`、`SiLU` 与 Softmax；`Scalar Unit` 充当总调度员，按核内标量指令解码循环与同步事件，向 Cube、Vector 与搬运引擎派发任务。
- **显式片上暂存器（Scratchpad Memory）**：昇腾片上存储器不由硬件透明缓存控制，内核必须显式编排数据路径：输入先经 **L1 Buffer**，再送入 Cube 专属 **L0A / L0B** 缓冲，累加停留在 **L0C**；Vector 单元输入输出几乎全落在 **Unified Buffer（UB）** 中[^ascend-ub]。910B 与 910C 上每核 `UB` 默认 `192 KB`（310P 为 `128 KB`）[^ascend-ub]，融合算子若同时存活过多 FP32 张量就会触顶溢出。
- **MTE1 / MTE2 / MTE3 异步 DMA 引擎**：`MTE2` 负责从 HBM 拉入片上 `L1` 或 `UB`，`MTE1` 把 `L1` 切片喂给 `L0A/L0B`，`MTE3` 写回产物。由于三者队列独立，优秀内核可实现 **Cube 算当前块的同时，Vector 算上一块激活，MTE2 预取下一块权重**——即 **CV 并行**。
- **FRACTAL_NZ 分形排布**：为匹配 `Cube Unit` 对 `16×16` 连续块的读取习惯，昇腾常在权重加载期把普通布局 `ACL_FORMAT_FRACTAL_ND = 2` 转为分形布局 `ACL_FORMAT_FRACTAL_NZ = 29`[^ascend-nz]。非 16 倍数维度必须向 16 补零对齐。

| 硬件维度           | NVIDIA GPU SM（Ampere / Hopper / Blackwell） | 昇腾 DaVinci AI Core（910B / 910C / A5）    | 工程直接影响                                     |
| :----------------- | :------------------------------------------- | :------------------------------------------ | :----------------------------------------------- |
| **矩阵算力核**     | Tensor Core（MMA / WGMMA）                   | Cube Unit（`16×16×16` 分形块）              | 线性层维度需对齐（GPU 8/16B，NPU 16 块）         |
| **非线性与向量核** | CUDA Core + MUFU 超越函数                    | Vector Unit（解耦长向量引擎）               | NPU 需关注 `Cube` 与 `Vector` 核内流水重叠       |
| **控制发射模型**   | SIMT Warp 调度器                             | Scalar 标量核 + 异步流水队列                | 算子太碎均需靠 CUDA Graph / ACL Graph 减发射耗时 |
| **片上存储管理**   | Register + SMEM + 硬件 L1/L2 Cache           | 显式 `L1 / L0A / L0B / L0C` 与 `192 KB UB`  | 昇腾融合算子需精确预算 `UB` 驻留张量数           |
| **异步搬运引擎**   | TMA 多维张量异步拷贝（Hopper+）              | `MTE1 / MTE2 / MTE3` 三通道 DMA             | 需用双缓冲（Double Buffer）掩盖 HBM 延时         |
| **典型张量排布**   | 通用行/列主序 `ND`                           | 权重转 `FRACTAL_NZ (29)`，A5 亦支持双态输入 | 异构插件须在权重加载期完成格式转换               |
| **PyTorch 接入键** | 原生 `CUDA` 分发键 -> `forward_cuda`         | `PrivateUse1`（`OOT`）-> `forward_oot`      | 上层模型代码零改动即可跨端路由                   |

## Roofline 模型与 Prefill / Decode 两副面孔

把前面算子里的浮点运算量与显存读写量串成一根比率，就能画出现代大模型推理最重要的标尺——**算术强度（Arithmetic Intensity）**：

$$
I = \frac{\text{FLOPs}}{\text{Bytes}} \quad (\text{单位：FLOPs / Byte})
$$

任给一张加速卡，它有两个物理硬上限：峰值矩阵算力 $P_{\text{peak}}$（TFLOPS）与显存读写带宽 $BW_{\text{HBM}}$（TB/s）。二者相交处称作**拐点算术强度（Ridge Point）**：$I^* = P_{\text{peak}} / BW_{\text{HBM}}$。于是算子性能上限满足：

$$
P_{\text{attained}} = \min\!\left(P_{\text{peak}},\ I \cdot BW_{\text{HBM}}\right)
$$

以 DeepSeek FlashMLA 实测校准的 **NVIDIA H800 SXM5**（BF16 峰值 `990 TFLOPS`，HBM3 带宽 `3.35 TB/s`）[^flashmla-doc]与 **昇腾示例剖面**（`320 TFLOPS` / `1.60 TB/s`）为标尺，图 3 交互式演示了同一套 `d=4096, d_ff=11008` SwiGLU FFN 在不同批量下的位移与昇腾 CV 流水重叠效果。

顺着图 3 读出三条关键规律（BF16 每元素占 2 字节，三矩阵权重共 `258 MiB`）：

- **Decode 阶段（$M=1$）**：为生成 1 个词元依然要读取全量 `258 MiB` 权重，每读 2 字节只做 2 次乘加，$I = 1.00\;\text{FLOP/B}$。H800 上算力利用率仅有 `3.35 / 990 = 0.3%`（910B 示例仅 `0.5%`），计算单元几乎完全在等 HBM 送数。
- **中等批大小（$M=64$）**：权重被 64 个词元分摊，算术强度升至 `62.86 FLOP/B`（H800 达 `210.6 TFLOPS`，仅 21.3% 峰值），依然死死停在拐点 `295.5` 左侧的带宽斜坡上。
- **Prefill 阶段（$M=4096$）**：权重在片上充分复用，算术强度越至 `1893.85 FLOP/B`，稳稳跨过双硬件拐点进入水平算力上限区；若进一步启用昇腾异步 **CV（Cube + Vector）双流水重叠**[^ascend-prefill]，可把 Vector 激活延迟藏进 Cube 矩阵乘窗口内，进一步压缩分块耗时。

## NumPy 核心实现与双硬件源码对照

下面给出独立可运行的 NumPy 核心实现，验证图 1 的 `[B=2, S=4, D=8]` 前向张量形状与图 3 的 SwiGLU 双平台 Roofline 数值；本地可用 `uv run --with numpy python` 直接运行复现：

```python
import numpy as np

rng = np.random.default_rng(7)
B, S, D, D_kv, D_ff = 2, 4, 8, 4, 16
X = rng.normal(0.0, 1.0, (B, S, D))
X_norm = X / np.sqrt(np.mean(X**2, axis=-1, keepdims=True) + 1e-6)
Q = X_norm @ rng.normal(0.0, 0.2, (D, D))
K = X_norm @ rng.normal(0.0, 0.2, (D, D_kv))
V = X_norm @ rng.normal(0.0, 0.2, (D, D_kv))
W_gate, W_up = rng.normal(0.0, 0.2, (D, D_ff)), rng.normal(0.0, 0.2, (D, D_ff))
W_down = rng.normal(0.0, 0.2, (D_ff, D))
gate = X_norm @ W_gate
silu_gate = gate / (1.0 + np.exp(-gate))
Y = X + (silu_gate * (X_norm @ W_up)) @ W_down
assert Q.shape == (2, 4, 8) and K.shape == (2, 4, 4) and Y.shape == (2, 4, 8)

wt_bytes = 3 * 4096 * 11008 * 2
for M in (1, 64, 4096):
    flops = 2 * M * 3 * 4096 * 11008
    bytes_io = wt_bytes + M * (4 * 4096 + 2 * 11008) * 2
    ai = flops / bytes_io
    print(f"M={M:4d}: AI={ai:7.2f} FLOP/B | H800={min(990.0, ai * 3.35):6.2f} TF | 910B={min(320.0, ai * 1.60):6.2f} TF")
```

实测输出与图 3 完全吻合：

```text
M=   1: AI=   1.00 FLOP/B | H800=  3.35 TF | 910B=  1.60 TF
M=  64: AI=  62.86 FLOP/B | H800=210.57 TF | 910B=100.57 TF
M=4096: AI=1893.85 FLOP/B | H800=990.00 TF | 910B=320.00 TF
```

在生产推理引擎中，同一套模型通过 `CustomOp` 按运行时平台自动分派到 NVIDIA CUDA 与昇腾 CANN 核函数[^vllm-customop][^ascend-platform][^ascend-reg][^ascend-ops]：

```python

    out = torch.empty(x.shape[:-1] + (d,), dtype=x.dtype, device=x.device)
```

## 代价与工程边界

把同一套 Roofline 与双硬件认知放进真实生产系统时，有三个边界条件最容易踩坑：

- **理论带宽不等于实际有效带宽**：标称 `3.35 TB/s` 反映的是连续大块读写；当张量切得过于细碎（例如未合并的跨步索引或小批量 GEMV），实测有效带宽可能掉到标称值的 60% 以下，同时未捕获算子图时每次 Python Kernel Launch 还会额外叠加微秒级调度间隙（这正是两家都强依赖 `CUDA Graph` 与 `ACL Graph` 的原因）。
- **昇腾分形排布与片上 `UB` 的双重硬约束**：910B/A2 与 910C/A3 系列在推理加载期偏向用 `WeightLayoutPolicy` 把权重转为 `FRACTAL_NZ`，到 A5 才在硬件层面进一步扩展了对混合布局及 `FP8/MXFP4` 权重的原生支持[^ascend-hw]；另一方面，每核 `192 KB` `UB` 意味着在写融合 Triton/Ascend C 内核时必须严格限制中间活张量个数与分块宽度[^ascend-ub]。
- **纯 FFN 只是热身，真正的长序列炸弹在 Attention**：本节还没展开长序列词元交互与缓存复用。一旦序列长度拉长到数万，不仅要做两两相似度矩阵，还要把历史 Key 和 Value 缓存在显存里并在每步解码全部重读一遍——那才是真正把 HBM 空间与带宽烧穿的主力。

<details>
<summary>参考答案</summary>

权重读取总量缩小为原来的 $0.5 / 2 = 1/4$。在 `M=1` 时激活字节微乎其微，总搬运字节同样近似降到 $1/4$，而乘加浮点次数不变，因此算术强度从约 `1.00` 升至约 `4.00 FLOPs/Byte`（接近 `4x` 提速潜力）。但它依然远低于 `295.5` 的拐点，所以 `M=1` 量化解码依然牢牢处于 **访存受限区间**——这也解释了为何单用户解码时 W4 权重量化几乎直接带来接近线性于带宽缩减倍数的延迟收益。

</details>

**自测 2**：代入上文 `d=4096, d_ff=11008` 的 SwiGLU Roofline 公式，估算需要把批大小 $M$ 拉到多大，H800 SXM5 才能跨过 `295.5 FLOPs/Byte` 拐点？

<details>
<summary>参考答案</summary>

按公式 $I(M) = \frac{2M \cdot 3 d d_{\text{ff}}}{2 \cdot 3 d d_{\text{ff}} + 2M(4d + 2d_{\text{ff}})} = 295.5$ 求解，权重字节固定为 `270,532,608 B`，每增加 1 个词元仅叠加 `76,784 B` 激活读写。解得临界批量 $M \approx 323$ 个词元，也就是说当连续批处理并发不足三百余词元时，FFN 在 H800 上本质上仍是靠 HBM 带宽而不是 Tensor Core 峰值跑速度。

</details>
