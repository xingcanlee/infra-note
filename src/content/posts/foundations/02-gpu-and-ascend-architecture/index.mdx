如果不先弄清芯片内部的调度机制与存储层级，“调高 Occupancy（占用率）”“消除 Bank Conflict（存储体冲突）”或“防止片上缓冲溢出”就只是一堆孤立的口诀。离开微架构语境，我们很难判断某条规则何时加速、何时反过来拖慢吞吐[^modular-gpu]。

理解底层行为，先要区分两个维度：**Execution Model（软件执行模型）**规定程序员如何把并行工作划成协作块；**Hardware（物理芯片硬件）**决定这些任务最终落到哪类计算单元和片上暂存。

把这两层拆开后，就能看清两条硬件路线的差异。后文将并排对照 NVIDIA **SM（Streaming Multiprocessor，流式多处理器）**与华为昇腾 **DaVinci AI Core（达芬奇算力核心）**在调度、存储与矩阵计算上的设计。

## 执行模型与物理硬件的解耦映射

在 NVIDIA GPU 上，**CUDA（Compute Unified Device Architecture，通用并行计算架构）**把计算网格组织成四个自底向上的软件逻辑层次。运行时再将这些层次自动铺展到芯片的各个 SM 上[^modular-gpu]。

最底层是 **Thread（线程）**，即逻辑上的最小执行单位。遵照 **SIMT（Single Instruction, Multiple Threads，单指令多线程）**模型，整个 Kernel 只写一份代码，各线程凭内置坐标计算自己要读写的数据偏移。

每 32 个相邻线程打包为一个 **Warp（线程束）**，它是 SM 真正的最小指令发射单位。调度器每次挑出一个 Warp，让 32 个线程在同周期执行同一条指令。若 `if / else` 分支让组内线程走向不同路径，硬件只能按掩码串行执行各分支，产生 **Warp Divergence（分支分化）**损耗。

多个 Warp 组成一个 **Thread Block（线程块，简称 CTA，CUDA Thread Block）**，常见上限为每块 1024 线程。块内线程可以通过 **SMEM（Shared Memory，片上共享内存）**交换数据并同步等待，且整个块会完整绑定到同一台 SM 直至结束。

顶层的 **Grid（网格）**包含一次 Kernel **Launch（启动）**释放出的全部 Thread Block，不同块之间无法直接共享 SMEM。只要切分出足够多独立的块（远多于 H100 的 132 个 SM），硬件就能自动把空出槽位派给后续块，使同一份源码适配不同规模的卡型。

华为昇腾 DaVinci AI Core 走上了另一套软硬件协同路线。昇腾没有 32 线程锁步的 Warp 池，它的软件发射以 **Block（计算核块）**为调度粒度，直接映射到物理核组上执行[^ascend-prefill]。以 Ascend 950 的 `1C2V` 架构为例，每个核组包含 1 个标量控制核、1 个矩阵核与 2 个向量核[^flashmla-ascend]。

其中 Scalar 标量核顺序读取指令流，向相互解耦的数据搬运引擎与算力流水线写入异步任务描述符。Cube 矩阵单元负责乘累加，两个 Vector 向量核则独立运行 **SIMD（Single Instruction, Multiple Data，单指令多数据）**长向量指令。图 1 展示了两套硬件从核内暂存、全卡 L2 Cache 到片外 **HBM（High Bandwidth Memory，高带宽显存）**的物理映射。

在左列的 NVIDIA H100 SM 内部，需区分软件的 CTA 与硬件的 **Processing Block（SM 物理处理块）**。每台 SM 物理上分为 4 个对称处理块，各自独享 1 个 Warp 调度器、寄存器分片和算力单元。4 个块共用整台 SM 的 **SRAM（Static Random-Access Memory，静态随机存取存储器）**池，GPU 把 CTA 派给 SM 后再由其分派到 4 个处理块并发执行[^modular-gpu]。

右列的昇腾芯片同样具备跨核共享的 L2 Cache，但核内没有硬件自动管理的 L1 Cache。Cube 侧使用专用的 `L1 -> L0A/L0B -> L0C` 缓冲层级，Vector 侧各自独占一块 192 KB 的 **UB（Unified Buffer，片上统一缓存）**[^ascend-ub]。片上与 HBM 之间的数据流全靠程序员显式编排搬运通道完成。

## 核内如何隐藏访存延迟

无论是 GPU 还是 NPU，从片外 HBM 拉取一批数据往往需要数百个时钟周期。要防止昂贵的矩阵单元空等数据，先要看清计算核心内部的硅片排布。

图 2 对照了单台 H100 SM 与单簇昇腾 `1C2V` 核组的物理模块。左侧 SM 包含 4 个对称处理块、共享 SRAM 与异步搬运引擎 **TMA（Tensor Memory Accelerator，异步张量搬运引擎）**。右侧则由 Scalar 统一驱动 1 个 Cube 与 2 个 Vector 通路。

![NVIDIA H100 单 SM 四处理块布局与华为昇腾 DaVinci 1C2V 单核组硬件模块布局对照](./diagrams/02-sm-vs-aicore-floorplan.drawio '图 2：单核硅片微架构布局对照——NVIDIA H100 SM (4×Processing Block) vs 昇腾 AI Core (1C2V)')

NVIDIA SM 依靠**高驻留 Warp 池与零开销上下文切换**来掩盖访存延迟。H100 每台 SM 配备 256 KB **Register File（寄存器堆）**，可容纳 65,536 个 32-bit 寄存器。由于全部驻留线程的上下文常驻其中，SM 能同时挂起多个 Thread Block。

一旦某个 Warp 因等待 HBM 数据而 **Stall（流水线停顿）**，调度器无需像操作系统那样压栈保存现场，下一周期就能直接改发另一个就绪 Warp，把访存等待掩盖在计算流水线背后。

定义 **Occupancy（占用率）**为一台 SM 当前实际驻留的活跃 Warp 数与硬件上限（H100 为 64 个 Warp / SM）之比：

$$
\text{Occupancy} = \frac{\text{Active Warps per SM}}{\text{Maximum Active Warps per SM}}
$$

单台 SM 最终能并排装进多少个 Thread Block，受限于最先触顶的那道资源上限。硬件会同时核对四项配额：每 SM 线程与 Warp 上限、Block 槽位上限（如 32 个）、单块寄存器总数，以及每块申请的 SMEM 字节数[^modular-gpu]。

高 Occupancy 只有在调度器缺乏就绪 Warp 时才带来收益。当驻留 Warp 已足以填满流水线空窗时，继续堆高驻留数反而会摊薄每块分到的寄存器和 SMEM。在 FlashAttention 等高性能算子中，开发者宁可把 Occupancy 压到 25%，也要多申请片上空间把累加器留在核心内，省下反复读写 HBM 的时间依然合算。

相比之下，华为昇腾 AI Core 靠软件编排 **Ping-Pong（乒乓双缓冲）**与 `1C2V` 异步流水重叠来掩盖延迟。因为没有几十个驻留线程束交替顶班，Scalar 核会把搬运与计算拆开，异步推入 **MTE（Memory Transfer Engine，数据搬运引擎）**和算力队列[^ascend-prefill]。

一条完整的矩阵算子流水分六步推进：MTE2 从 HBM 读入片上，MTE1 从 L1 送入 L0A/L0B，Cube 乘累加进 L0C。随后 **FixPipe（矩阵后处理与直通搬运管线）**迁出至 UB，最后由 Vector 归约并经 MTE3 写回。为防止同一缓冲既读又算而空等，开发者把 L1 或 UB 对半切为 Buf A 与 Buf B；Cube 计算 Buf A 时，MTE2 并行预取下一块到 Buf B。

与此同时，两个 Vector 核把上一块留在 `UB` 里的 Softmax 归约掩盖在当前矩阵乘窗口内执行，即 **CV 重叠**。这里还要兼顾硬件队列深度：昇腾 950 的单个 Vector 核最多只允许 16 个未完成 `MTE2` 请求。配成 `1C2V` 双向量核，正是为了分摊搬运发射、反量化与 `FixPipe` 迁出压力[^flashmla-ascend]。图 3 用交互时序演示了这两套微架构掩盖延迟的过程。

## 存储金字塔与访存合并约束

加速卡内的存储层次从算力核心向外层层展开，遵循同一条权衡曲线：离计算单元越近，延时越低、带宽越宽、单核容量越小；离核心越远，容量扩大几个数量级，但带宽骤缩且延时跳升至数百个时钟周期[^modular-gpu]。下表汇总了 Hopper 架构 H100 GPU 与昇腾 AI Core 的典型存储分级特征。

| 层级角色 | NVIDIA H100 分级 | 容量 / 带宽 / 延迟           | 昇腾 AI Core 分级  | 管理与硬件约束       |
| :------- | :--------------- | :--------------------------- | :----------------- | :------------------- |
| 私密暂存 | Registers        | 256 KB/SM · ~1 cyc           | `L0A`/`L0B`/`L0C`  | 编译器管；L0C 只累加 |
| 核内协作 | SMEM + L1 Cache  | 256 KB · 20 TB/s · ~25 cyc   | `L1` + 192 KB UB   | 32-Bank / 防 UB 溢出 |
| 全芯末级 | L2 Cache         | 50 MB · 12 TB/s · ~200 cyc   | 共享 L2（~5 TB/s） | 跨核复用权重与索引   |
| 片外显存 | HBM3             | 80 GB · 3.35 TB/s · 400+ cyc | HBM（ND / 分形）   | 权重、KV 与激活载体  |

这张金字塔里有两个细节直接决定代码能否跑出纸面带宽。第一处要分清硬件自动管理的 L1/L2 Cache 与软件显式管理的片上暂存。在 GPU 上，SMEM 与 L1 共用同一片 256 KB 物理 SRAM，L1 由硬件按局部性透明缓存，生命周期不受程序控制。

SMEM 则由程序员按 Thread Block 显式申请管理，并组织成 32 个并行存储 **Bank（存储体）**。若同一 Warp 内多个线程同拍访问同一 Bank 的不同地址，硬件只能串行化，即 **Bank Conflict（存储体冲突）**。高吞吐 Kernel 常通过 **Swizzling（异或地址交错重排）**打散地址，多线程同读同一地址则会触发硬件广播而不冲突。

昇腾 AI Core 内部没有透明的硬件 L1 Cache。所有在 Vector 中参与非线性运算的数据，都必须提前算好字节数并向 192 KB `UB` 申请槽位。只要内循环常驻的浮点中间张量超出余量，编译或运行时就会直接报 `UB overflow` 错误[^ascend-rope]。

第二处是决定 HBM 有效吞吐的 **Memory Coalescing（访存合并）**规则。在 NVIDIA GPU 上，全局显存加载以 32 字节对齐的 **Sector（缓存扇区）**作为硬件最小传输单元[^modular-gpu]。当 Warp 内 32 个线程各自读取 1 个 4 字节 `float32`（共 128 B 载荷）且地址紧凑相邻时，硬件仅拉回 4 个 Sector，有效带宽利用率达到 100%。

如果把起始地址仅仅顺延 4 字节，第 31 号线程就会滑进第 5 个 Sector，迫使总线搬运 160 B。若步长扩大到 8 个 `float32`（每线程跨 32 字节），32 个线程便各自独占一个 Sector。此时 HBM 被迫搬回整整 1024 B 却只用到 128 B，超过八成带宽被白白吞没。

华为昇腾 AI Core 内部由 **BIU（Bus Interface Unit，总线接口单元）**负责打包发起访存指令。FlashMLA 实测揭示了一条硬约束：BIU 只有当源地址（即全局主显存 GM）与片上目的地址双双连续时，才会合并成高效突发事务[^flashmla-ascend]。

如果从 HBM 读出连续向量后，在 `MTE2` 搬往 `L1 Buffer` 的路上直接按非连续步长写成矩阵分形排布，BIU 会放弃合并并导致 L2 带宽掉档。因此昇腾稀疏算子的标准解法是先用 `MTE2` 把连续切片搬进 `UB`，由 Vector SIMD 原地完成 `ND2NZ`（标准多维排布转 16×16 分形排布）转换，再连续迁往 `L1` 喂给 Cube。图 4 演示了双平台的访存合并与存储金字塔层级。

## 矩阵计算引擎与硬件激活契约

大模型推理 99% 以上的算力由矩阵乘消耗，通用标量 **ALU（Arithmetic Logic Unit，算术逻辑单元）**无法承担这一载荷。因此两类芯片都内置了围绕低精度 **Tile（分块）**设计的专用矩阵加速引擎。

NVIDIA Tensor Core 历经三代演进，早期在 Ampere 上采用 Warp 级指令 **MMA（Matrix Multiply-Accumulate，矩阵乘累加）**。Hopper 推出异步指令 **WGMMA（Warpgroup MMA，线程束组异步矩阵指令）**，Blackwell 则演进到 `tcgen05` 与 `UMMA`。昇腾 AI Core 则配备 16×16×16 `Cube` 脉动阵列。

两套引擎在指令语义上共享同一数学模板：对小尺寸分块执行融合乘累加 $D = A \times B + C$[^modular-gpu]。如果沿归约维一直用 16-bit 做运行和，狭窄的指数或尾数极易发生上溢或大数吞小数。因此 Tensor Core 与 Cube 的累加器都接收低精度输入分块 $A, B$，同时默认向 **FP32（32 比特单精度浮点）**累加器写入中间和 $C, D$。

仅仅把张量声明为 `bfloat16` 或 `float8` 并不能自动跑满标称 TFLOPS。要激活矩阵引擎并维持稳态吞吐，必须兑现对齐与排布契约，并按硬件偏好的几何块组织数据，如图 5 所示。

![矩阵指令 D=A×B+C 几何、SMEM Swizzle 消 Bank 冲突与昇腾 FRACTAL_NZ 分形布局](./diagrams/02-tensor-core-vs-cube-tiling.drawio '图 5：矩阵分块几何（D = A × B + C）、SMEM Swizzle 与昇腾 FRACTAL_NZ 分形布局')

对照图 5 下方的内存重排，双平台在形状对齐与片上排布上分歧明显。NVIDIA Tensor Core 依托 `TMA` 读取行或列主序的 **ND（N-Dimensional，标准多维）**张量。硬件要求指针与跨步对齐到 16 字节，且矩阵维整除 `m16n8k16` 等分块。数据进入 SMEM 后，再通过 Swizzle 重排躲避 32-Bank 冲突。

昇腾 Cube 单元则要求权重采用 **`FRACTAL_NZ`（16×16 Z 字形分形布局）**，推理引擎通常在加载权重时就把 `FRACTAL_ND` 离线重排为 16×16 连续分形块[^ascend-nz]。前向时把矩阵 $M$ 维凑够 64，Ascend 950 就能以 4096 次 **FMA（Fused Multiply-Add，融合乘加）**/周期吃满 Cube 阵列。若关闭 **HF32（High-Precision Float32，19 比特高速融合浮点）**模式，算力则会退回慢速精确路径[^flashmla-ascend]。

更深层的分水岭落在硬件代际的非对称缩放上。Blackwell B200 将矩阵乘算力再次倍增，但 **MUFU（Multi-Function Unit，特殊函数单元）**的指数吞吐仍停在每周期 16 次，SMEM 读带宽也停在每周期 128 字节。为此 GPU 专门引入 256 KB **TMEM（Tensor Memory，张量内存）**接管巨型累加器，为寄存器减压[^fa4-paper]。

昇腾 AI Core 的 FP32 累加结果存放在 256 KB `L0C` 缓冲内。硬件上 `L0C` 只支持作下一拍 **MMAD（Matrix Multiply-Add，Cube 矩阵乘累加指令）**的累加器，或经 `FixPipe` 单向迁出。它无法像 GPU 寄存器那样就地乘以标量系数[^flashmla-ascend]。遇到在线 Softmax 等需要动态重缩放的场景，必须由 `FixPipe` 迁往 `UB`，再由双 Vector 核并肩分摊归约与重缩放带宽。

## 微架构定量建模与双端分发

下面的自包含 Python 脚本基于真实芯片参数定量校核本篇的三项结论。前两项验证 H100 上轻量算子（100% Occupancy）与 FlashAttention 大分块（25% Occupancy）的 SM 驻留计算。同时核对图 4 中四种访存模式的 32 字节 Sector 数与有效带宽比。

第三项复现 `vllm-ascend` 的 **RoPE（Rotary Position Embedding，旋转位置编码）**算子在 `rope_dim = 128` 下的 `UB` 分块上限[^ascend-rope]。同时算出 Ascend 950 单 Vector 核的 `FixPipe` 搬算平衡阈值 `B_TOPK = 73.14`[^flashmla-ascend]：

```python
import numpy as np

# 1. H100 SM Residency & Occupancy (Vector vs FlashAttention)
MAX_WARPS, MAX_BLOCKS, MAX_REGS, MAX_SMEM = 64, 32, 65536, 228 * 1024
for name, threads, regs, smem in [
    ("Vector_RMSNorm", 256, 32, 8 * 1024),
    ("FlashAttn_Tile", 256, 128, 112 * 1024),
]:
    warps_blk = threads // 32
    resident = min(
        MAX_BLOCKS,
        MAX_WARPS // warps_blk,
        MAX_REGS // (threads * regs),
        MAX_SMEM // smem,
    )
    active_w = resident * warps_blk
    print(
        f"{name:15s}: blk/SM={resident}, active_warps={active_w}/64, "
        f"Occupancy={active_w / MAX_WARPS:5.1%}"
    )

# 2. 32-thread Warp global memory coalescing into 32-byte sectors (float32 = 4B)
tids = np.arange(32)
patterns = [
    ("contiguous a[tid]", tids * 4),
    ("misaligned a[tid+1]", (tids + 1) * 4),
    ("strided a[tid*2]", tids * 8),
    ("strided a[tid*8]", tids * 32),
]
for label, addrs in patterns:
    sectors = len(np.unique(addrs // 32))
    fetched = sectors * 32
    print(
        f"{label:20s}: sectors={sectors:2d}, fetched={fetched:4d} B, "
        f"useful={128 / fetched:5.1%}"
    )

# 3. Ascend 192 KB UB tile budget (rope_dim=128, safety=0.5) & 950 1C1V FixPipe
ub_avail = int(192 * 1024 * 0.5) - 2 * 64 * 4  # 97,792 B after shared cos/sin row
for layout, n_live, width in [("NeoX_half", 8, 64), ("Interleaved_3D", 10, 128)]:
    per_head = n_live * width * 4
    pow2 = 1 << ((ub_avail // per_head).bit_length() - 1)
    print(
        f"Ascend UB {layout:14s}: {per_head:4d} B/head -> "
        f"max={ub_avail // per_head:2d}, pow2_tile={pow2}"
    )
print(f"Ascend 950 1C1V FixPipe crossover B_TOPK = {1024.0 / (16.0 - 2.0):.2f}")
```

脚本输出与上文公式及上游实测吻合。在 `rope_dim = 128` 与 50% `UB` 安全余量下，NeoX 半段布局峰值驻留 8 个半宽张量，最多批处理 `pow2_tile = 32` 个头。若强开 64 个头，就会像昇腾 910B 实测那样触发 `UB` 溢出[^ascend-rope]；而交错 3D 布局因多占 2.5 倍空间，只能退到 16 个头。

上层推理引擎需要在不改动模型代码的前提下，把同一套算子接口路由到这两套截然不同的微架构。以 `vLLM` 与 `vllm-ascend` 为例，`RMSNorm`、`SiluAndMul` 等基础算子统一继承自 `CustomOp`[^vllm-customop][^vllm-norms]。

当 `vllm-ascend` 将 `NPUPlatform` 注册为 `PlatformEnum.OOT` 后，就会激活 PyTorch `PrivateUse1` 扩展分发键[^ascend-platform][^ascend-reg]。借这套 **Out-of-Tree（OOT 硬件插件后端）**机制，模型前向可无感从 CUDA C++ 切往 Ascend 融合算子[^ascend-ops]：

```python
# vllm/model_executor/custom_op.py:194-205 (vllm@bb23c0a8)
if current_platform.is_rocm():
    return self.forward_hip
elif current_platform.is_out_of_tree():
    return self.forward_oot
else:
    return self.forward_cuda

# vllm/model_executor/layers/activation.py:146-151 (NVIDIA GPU SwiGLU)
def forward_cuda(self, x: torch.Tensor) -> torch.Tensor:
    d = x.shape[-1] // 2
    out = torch.empty(x.shape[:-1] + (d,), dtype=x.dtype, device=x.device)
    self.op(out, x)  # torch.ops._C.silu_and_mul
    return out

# vllm_ascend/ops/activation.py:37-40 (vllm-ascend@3649b8ff, 昇腾 NPU SwiGLU)
class AscendSiluAndMul(SiluAndMul):
    def forward_oot(self, x: torch.Tensor) -> torch.Tensor:
        out = torch_npu.npu_swiglu(x)
        return out
```

| :----------- | :------------------------ | :------------------------- | :--------------------------- |
| 并行执行单元 | 32 线程 SIMT Warp         | Scalar 派发 + `1C2V` 核组  | Warp 避分歧；NPU 避空泡串行  |
