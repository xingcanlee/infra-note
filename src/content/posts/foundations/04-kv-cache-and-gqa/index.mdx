自回归语言模型生成第 1001 个 token 时，注意力层需要与前面 1000 个历史 token 的 **Key（键）**和 **Value（值）**交互，而这批历史键值对前几步已经算出且不再改变。若不缓存，每步都得重算整段前缀，累计投影计算量按 $O(N^2)$ 增长。把历史键值留在片外显存后，64 层多头注意力在长上下文与大并发下又会迅速占满 **HBM（High Bandwidth Memory，高带宽显存）**容量与带宽。

## 增量解码与全前缀重算的工作量对比

把生成过程中的历史键和值留在显存里逐槽追加，称作 **KV Cache（Key-Value Cache，键值缓存）**。由于第 $t$ 步的查询向量 $Q_t$ 只算当前最后一行注意力分数，而前面 $1 \dots t-1$ 行的因果掩码只依赖各自左侧的历史键，增量写缓存与重算前缀在数学上等价。

图 1 按解码步 $t = 1 \dots 4$ 对比了增量追加与全量重算的投影次数。有缓存时每步只算 1 组 $Q_t$ 与 $(k_t, v_t)$ 并填入空槽，4 步累计只需 4 次投影；若不做缓存，仅第 4 步就要重算 4 个 token 再丢弃前 3 行，累计达 10 次，相差 2.50 倍。

放在带提示词前缀的推理场景里，差距会拉得更大。设提示词长 $T_{\text{prompt}}$、自回归生成 $T_{\text{gen}}$ 步，无缓存重算的前缀长度呈等差数列递增。当取 $T_{\text{prompt}} = 4$、$T_{\text{gen}} = 4$ 时，重算路径累计执行 $5 + 6 + 7 + 8 = 26$ 次投影，开启缓存则只需计算 4 个新 token 的键值，运算量差距拉大到 6.50 倍，并随总长扩至 $O(T)$ 倍。

## 64 层 MHA 的显存与带宽开销

省下了重复计算，代价是必须在显存里常驻不断增长的 KV 张量。设模型共有 $L$ 个 Transformer 层，每层缓存 $n_{kv}$ 个键值头，单头向量长度为 $d_{\text{head}}$，每个元素占 $b_{\text{dtype}}$ 字节（BF16 精度取 2 字节）。由于每层都需要同时保存 Key 与 Value 两个形状等价于 `[T, n_kv, d_head]` 的张量，单个 token 在全模型中占用的 KV 缓存字节数为：

$$
M_{\text{tok}} = 2 \cdot L \cdot n_{kv} \cdot d_{\text{head}} \cdot b_{\text{dtype}}
$$

代入主流 64 层标准 **MHA（Multi-Head Attention，多头注意力）**模型（$L = 64$、$n_q = n_{kv} = 64$、$d_{\text{head}} = 128$、$b_{\text{dtype}} = 2$），每个 token 占用 $2 \times 64 \times 64 \times 128 \times 2 = 2{,}097{,}152\text{ B} = 2048.0\text{ KiB/token} = 2.0\text{ MiB/token}$。一旦服务 16 路并发且序列长达到 32K（32768），全模型缓存立即膨胀到 $16 \times 32768 \times 2.0\text{ MiB} = 1024.0\text{ GiB}$，即 1.0 TiB，远超单张 80 GB 显存卡的容量。

比显存容量更隐蔽的是单步解码的带宽墙。以批大小 $B = 1$、上下文长度 $T$ 为例，每层注意力只为当前 1 个新 token 计算输出：查询 $q_t$ 的形状是 `[n_q, d_head]`，历史键和值各为 `[T, n_kv, d_head]`。统计 $Q K^\top$ 与 $P V$ 两次核心乘加运算，除以读取历史 $K/V$、读写当前 $Q/O$ 及追加新 $(k_t, v_t)$ 的总字节数，得到解码注意力的算术强度：

$$
I_{\text{attn}} = \frac{4 \, T \, n_q \, d_{\text{head}}}{\bigl(2(T + 1)\, n_{kv}\, d_{\text{head}} + 2\, n_q\, d_{\text{head}}\bigr)\cdot b_{\text{dtype}}}
$$

在 BF16 精度（$b_{\text{dtype}} = 2$）且上下文较长（$T \gg n_q / n_{kv}$）时，括号内的常数项可以略去，算术强度直接渐近化简为查询头数与键值头数的比值 $g$：

$$
I_{\text{attn}} \approx \frac{4\,T\,n_q\,d_{\text{head}}}{4\,T\,n_{kv}\,d_{\text{head}}} = \frac{n_q}{n_{kv}} = g
$$

这行渐近关系直接决定了解码注意力的 Roofline 位置：在标准 MHA 下每组键值头只服务 1 个查询头（$g = 1$），代回 $T = 2048$ 的精确公式算得算术强度只有 0.999 FLOP/B。无论算力核多强，只要每次搬进 2 字节历史 KV 只做 2 次乘加就丢弃，硬件就几乎全部时间在等 HBM 搬运。

## MQA 与 GQA 的头共享权衡

既然标准 MHA 的瓶颈在于每个查询头都要从显存里拉取一份专属的 Key 和 Value，最直接的压缩办法就是减少键值头数 $n_{kv}$，让多个查询头共用同一组 KV。把 $n_q$ 个查询头均匀划分为 $n_{kv}$ 组，每组包含 $g = n_q / n_{kv}$ 个查询头。图 2 用等比例宽度的张量条对比了标准 MHA、**GQA（分组查询注意力）**与 **MQA（多查询注意力）**的头映射和缓存体积。

![MHA（8:8=100%）、GQA（8:2=25%）与 MQA（8:1=12.5%）等比例 KV 容量对比](./diagrams/04-mqa-gqa-arch.drawio '图 2：MHA（8:8=100%）、GQA（8:2=25%）与 MQA（8:1=12.5%）头映射与缓存字节占比等比对照')

沿着图 2 向下压缩键值头数，硬件收益和模型质量呈现一条折中曲线。在 MHA（$g = 1$，$n_{kv} = n_q$）模式下，每个查询头独占一套 KV，容量与访存需求最大。

2019 年 Shazeer 提出的 **MQA（Multi-Query Attention，多查询注意力）**[^mqa-paper]让层内所有查询头共享唯一一对 $(K_0, V_0)$。在 **TPUv2（Google Tensor Processing Unit v2）**上，它将贪心解码耗时从 46 μs/token 压到 3.8 μs/token。Beam-4 搜索耗时也同步从 203 μs 降至 32 μs。

对应到前面的 64 层模型，MQA 把单 token 缓存缩小 64 倍至 32.0 KiB/token。16 路并发 32K 上下文总显存从 1024.0 GiB 降为 16.0 GiB，而 $T=2048$ 时的解码算术强度跃升至 62.031 FLOP/B。

为了避免只留 1 个 KV 头带来的训练收敛风险，Ainslie 等人在 2023 年提出折中的 **GQA（Grouped-Query Attention，分组查询注意力，$1 < g < n_q$）**[^gqa-paper]。它对已训练的 MHA 检查点按组均值池化，并补充 5% 计算量持续微调，在接近 MQA 解码速度的同时把评测质量拉回 MHA 水平。

压缩 $n_{kv}$ 能提高矩阵单元利用率，因为同组 $g$ 个查询向量会拼成 `[g, d_head]` 小矩阵。片上读出 1 份共享 $K$ 或 $V$ 块后可同时乘以全部 $g$ 个查询头，把算术强度放大接近 $g$ 倍。以 64 层模型配 GQA-8（$g=8$）为例，单 token 缓存降至 256.0 KiB/token，16 路 32K 总量降至 128.0 GiB。同时，$T=2048$ 解码算术强度抬升到 7.965 FLOP/B。

不过，头共享本质上是在用独立键值的表达自由度换取显存与带宽空间。在几项经典对照实验中，这种表达力折中都有明确体现：

| 模型配置（来源）                        | 配置              | 代表指标对照                                                  |
| :-------------------------------------- | :---------------- | :------------------------------------------------------------ |
| 1B 语言模型（Shazeer 2019[^mqa-paper]） | MHA vs MQA        | PPL（困惑度，越低越准）29.9 vs 30.2（缩减头数升至 30.9–31.2） |
| T5-XXL 微调（Ainslie 2023[^gqa-paper]） | MHA / GQA-8 / MQA | 均分 47.2 / 47.1 / 46.6；解码 1.51 s / 0.28 s / 0.24 s        |
| 7B Dense（DeepSeek-V2[^dsv2-paper]）    | MHA / GQA-8 / MQA | MMLU 45.2/41.2/37.9；BBH 37.0/35.6/33.2；CEval 42.9/37.7/30.0 |

尤其当直接从零用 GQA 或 MQA 训练万亿级 token 时，模型在知识与推理基准上的得分会比 MHA 基线低几个百分点。即使压到 GQA-8，128.0 GiB 的并发缓存依然偏大，7.965 FLOP/B 也远低于芯片拐点。一旦开启 8 卡张量并行，像 MQA 或 GQA-4 这种头数少于卡数的配置还必须跨卡复制 KV，省下的容量又会被冗余占掉一半。

如何在保留独立注意力头的前提下把 KV 体积再压低一个数量级？这正是[《DeepSeek 架构演进》第 01 篇](../../deepseek/01-mla/)拆解 **MLA（Multi-Head Latent Attention，多头潜在注意力）**的切入点。

## 缓存等价性与 64 层带宽核验

下面用一段自包含 NumPy 脚本，在 MHA（$n_{kv}=8$）、GQA（$n_{kv}=2$）与 MQA（$n_{kv}=1$）下验证增量缓存与全前缀重算的等价性，并核对 64 层模型在 $T = 2048$ 下的容量与算术强度：

```python
import math
import numpy as np

def softmax(x, axis=-1):
    e = np.exp(x - np.max(x, axis=axis, keepdims=True))
    return e / np.sum(e, axis=axis, keepdims=True)

rng = np.random.default_rng(3)
d_model, n_q, T_p, T_g = 64, 8, 4, 4
X = rng.normal(0.0, 1.0, (T_p + T_g, d_model))
Wq = rng.normal(0.0, 0.1, (d_model, d_model))

for n_kv in (8, 2, 1):
    g, dh = n_q // n_kv, d_model // n_q
    Wk = rng.normal(0.0, 0.1, (d_model, n_kv * dh))
    Wv = rng.normal(0.0, 0.1, (d_model, n_kv * dh))
    kc, vc, cached_outs = [], [], []
    for t in range(T_p + T_g):
        qt = (X[t] @ Wq).reshape(n_q, dh)
        kc.append((X[t] @ Wk).reshape(n_kv, dh))
        vc.append((X[t] @ Wv).reshape(n_kv, dh))
        ka = np.repeat(np.stack(kc, axis=0), g, axis=1)
        va = np.repeat(np.stack(vc, axis=0), g, axis=1)
        probs = softmax(np.einsum("hd,khd->hk", qt, ka) / math.sqrt(dh))
        cached_outs.append(np.einsum("hk,khd->hd", probs, va).reshape(d_model))
    Q_all = (X @ Wq).reshape(T_p + T_g, n_q, dh)
    K_all = np.repeat((X @ Wk).reshape(T_p + T_g, n_kv, dh), g, axis=1)
    V_all = np.repeat((X @ Wv).reshape(T_p + T_g, n_kv, dh), g, axis=1)
    scores = np.einsum("thd,khd->htk", Q_all, K_all) / math.sqrt(dh)
    causal = np.tril(np.ones((8, 8), dtype=bool))[None]
    S_all = np.where(causal, scores, -np.inf)
    full_outs = np.einsum("htk,khd->thd", softmax(S_all), V_all).reshape(8, d_model)
    max_diff = float(np.max(np.abs(np.stack(cached_outs) - full_outs)))
    assert max_diff < 1e-13
    print(f"n_q={n_q}, n_kv={n_kv} (g={g}): max_abs_diff={max_diff:.2e}")

for name, n_kv in (("MHA", 64), ("GQA-8", 8), ("MQA", 1)):
    m_kib = (2 * 64 * n_kv * 128 * 2) / 1024
    ai = (4 * 2048 * 64 * 128) / ((2 * 2049 * n_kv * 128 + 2 * 64 * 128) * 2)
    b16_gib = m_kib * 16 * 32768 / 1048576
    print(
        f"{name:5s}: {m_kib:6.1f} KiB/tok | "
        f"B=16,32K: {b16_gib:6.1f} GiB | AI={ai:6.3f} FLOP/B"
    )
```

脚本运行输出如下，三组头映射的数值最大绝对误差均不超过 $1.22 \times 10^{-15}$（落在双精度浮点舍入误差范围内），容量与算术强度也与前文推导一致：

```text
n_q=8, n_kv=8 (g=1): max_abs_diff=1.11e-15
n_q=8, n_kv=2 (g=4): max_abs_diff=8.88e-16
n_q=8, n_kv=1 (g=8): max_abs_diff=1.22e-15
MHA  : 2048.0 KiB/tok | B=16,32K: 1024.0 GiB | AI= 0.999 FLOP/B
GQA-8:  256.0 KiB/tok | B=16,32K:  128.0 GiB | AI= 7.965 FLOP/B
MQA  :   32.0 KiB/tok | B=16,32K:   16.0 GiB | AI=62.031 FLOP/B
```

## 生产分页 KV 排布与双端调度

生产级推理引擎写入 KV Cache 时，需要绕开连续数组拼接的重分配开销。如果按最大上下文为每条请求预留连续显存，大量尾部空间会造成严重碎片；若每步重新分配并拷贝整段缓存，又会浪费大量显存带宽。

因此以 PagedAttention 为代表的框架借鉴了操作系统的虚拟内存分页[^paged-attn]，将逻辑连续的请求切分为固定大小的物理块（`block_size`）按需申领。每步前向时，调度器为新 token 算出全局一维槽位 `slot_mapping`（块号乘以块大小加块内偏移），再由底层融合算子按槽位原地执行 Scatter 写入。

图 3 并排对照了 `vLLM` GPU 与 `vllm-ascend` NPU 在这套分页缓存模型下的物理内存排布与读写通路。

![vLLM GPU 行主序分页池与 vllm-ascend 16x16 分形 KV 布局对比](./diagrams/04-gpu-vs-npu-kv-layout.drawio '图 3：vLLM GPU 行主序分页 KV 池与 vllm-ascend 16×16 分形布局对照')

在写入和读取两个环节上，两条硬件栈围绕[第 02 章](../02-gpu-and-ascend-architecture/)揭示的访存偏好做出了明确区分。`vLLM` GPU 路径的 `FlashAttentionImpl` 维护合并物理池。写缓存时它沿最后一维切出 Key 和 Value 视图，交给 `reshape_and_cache_flash` 按 `slot_mapping` 执行原地 Scatter 写入[^vllm-fa]。

GPU 池块内沿着 `head_size` 保持行主序连续排布。这既能匹配 32 字节 Sector 访存合并，也满足 **TMA（Tensor Memory Accelerator，异步张量搬运引擎）**的 16 字节对齐。读取时 CUDA Kernel 直接按组比例偏移复用同一份物理 KV 头，在 L2 Cache 中命中复用，避免在 HBM 里复制 $g$ 份副本。

在 `vllm-ascend` 路径中，标准注意力默认取 `block_size = 128`。它的缓存池形状定义为 `(2, num_blocks, block_size, num_kv_heads, head_size)`，部分融合场景可折叠为 16×16 分形。写入通过 `DeviceOperator.reshape_and_cache` 分发至 `npu_scatter_pa_kv_cache` 等算子。读取则由 `npu_fused_infer_attention_score_v2` 按组广播消费[^vllm-ascend-attn][^vllm-ascend-dev]。

```python
# vllm/v1/attention/backends/flash_attn.py:1422-1440 (vllm@bb23c0a8)
key_cache, value_cache = kv_cache.transpose(1, 2).split(self.head_size, dim=-1)
reshape_and_cache_flash(
    key, value, key_cache, value_cache, slot_mapping,
    self.kv_cache_dtype, layer._k_scale, layer._v_scale,

# vllm_ascend/device/device_op.py:298-305 (vllm-ascend@3649b8ff)

```

| 对比维度          | `vLLM` GPU（`bb23c0a8`）   | `vllm-ascend` NPU（`3649b8ff`） |
| :---------------- | :------------------------- | :------------------------------ |
| 物理缓存形状      | 合并 5D 池按行主序对齐     | 2 通道池（可折叠 16×16 分形）   |
| 槽位 Scatter 算子 | `reshape_and_cache_flash`  | `npu_scatter_pa_kv_cache`       |
| 分组读取机制      | Kernel 按组偏移片上复用 KV | 融合注意力算子原生分组读取      |

分页排布解决了历史 KV 的物理存储与读取效率，但在长序列 Prefill 或 Decode 过程中，注意力分数矩阵 $Q K^\top$ 依然按序列长度平方 $O(N^2)$ 增长。下一章[05 FlashAttention 与硬件对齐 Kernel](../05-flash-attention/)将介绍如何用片上在线归并把中间分数留在核心内，绕开 $O(N^2)$ 的显存读写墙。
