在[第 1 章](../01-heterogeneous-streams-and-events/)里，我们看到异步队列只能掩盖 CPU 发射等待，却无法减少算子数量。于是很多开发者想到打开 `torch.compile`，以为把模型编成一张计算图就能直接取代设备静态图。

实际推理工程远没有这么简单。在 PyTorch **Eager（逐算子直跑）** 模式下，系统同时要交两笔税。一是每个算子都要付一次主机发射耗时 $T_{\text{launch}}$；二是碎片算子每算完一步都要把中间结果写回 **HBM（High Bandwidth Memory，高带宽显存）**，下个算子再重读。

以大模型前馈网络常见的 SwiGLU（$\text{SiLU}(a) \odot b$）为例，设输入批量 $B = 8$、半隐维 $D = 5120$、BF16 单片张量占 $80\,\text{KB}$。Eager 下先算 `silu` 读 $a$ 写中间值，再算 `mul` 读中间值与 $b$ 写输出，来回跑了 5 趟 HBM（共 $400\,\text{KB}$）。

`torch.compile` 真正擅长的是把 `silu` 和 `mul` 融进同一段计算核里，把 5 趟搬运压成 3 趟（$240\,\text{KB}$）。但它并不能把整网一次打包下发，生产上仍需外包设备静态图。

## 字节码怎么变成计算图：Dynamo 与断图

想把日常写的 Python 模型代码变成可优化的计算图，第一步必须解决：Python 是动态解释语言，编译器怎么把张量算子抠出来？

### PEP 523 拦截与 Graph Break

PyTorch 2 在 ASPLOS 2024 论文[^pytorch2-paper]中系统阐述了 `torch.compile`。依托 **TorchDynamo** 与 **TorchInductor**，该方案在 180 多个模型上相对 Eager 取得推理 2.27 倍、训练 1.41 倍的几何平均加速。

其中 **TorchDynamo** 利用 Python **PEP 523（Frame Evaluation API，栈帧求值接口）** 在函数运行前拦住字节码流[^vllm-compile-doc]。Dynamo 遇到张量运算时不真正算数值，而是记录成 `torch.fx.GraphModule`（简称 FX 图），如图 1 所示。

```mermaid caption="图 1：TorchDynamo 字节码捕获、Dynamo Guard 校验与 Graph Break 切分路径"
flowchart TD
    F["PEP 523 拦截 Python 栈帧"] --> G{"命中已有<br/>Dynamo Guard?"}
    G -->|"命中"| R["直达缓存编译产物"]
    G -->|"未命中"| T["符号追踪字节码生成 FX 图"]
    T --> D{"遇数据依赖或<br/>.item() 断点?"}
    D -->|"是 (Graph Break)"| S["截断子图下发 -> Python 执行断点"]
    S --> T
    D -->|"否"| A["完整 FX Subgraph 移交 AOTAutograd"]
```

一旦代码里混入 `print(x.item())`、`torch.save` 或编译器看不懂的 C 扩展，Dynamo 就会触发 **`Graph Break`（局部断图）**。如图 2 所示，编译器会把断点前的 `g(x)` 与断点后的 `h(x)` 分别编成独立子图，中间退回 Python 跑完断点语句[^vllm-tc-blog]。

### 动态批大小：SymInt 与 Guard 陷阱

推理服务的批大小每步都在跳变，上一毫秒 4 个解码词元，下一毫秒涌入 512 个预填充词元。若编译时把维度写死为常量，每遇到新长度就得重编数秒，在线服务会直接卡死。

为此，PyTorch 用 **Symbolic Shapes（`SymInt`，符号整数）** 代表动态维度，并用 **`Dynamo Guard`** 核对后续请求形状是否仍匹配编译产物。图 3 与图 4 展示了 vLLM 抓图流程与 `tlparse` 抓出的守卫异常现场[^vllm-debug-doc]。

| 符号机制                     | 运行时行为与约束               | 在线风险与规避手段              |
| :--------------------------- | :----------------------------- | :------------------------------ |
| **Backed `SymInt` (`s0`)**   | 已知输入尺寸；分支注入模 Guard | 模余失效重编，用 `tlparse` 排查 |
| **Unbacked `SymInt` (`u0`)** | `nonzero()` 等数据依赖动态维   | 视图或尺寸校验触发 Graph Break  |
| **0/1 步长特化**             | 0 维或 1 维默认固化成字面常量  | `bs=1` 反复抖动；无 Guard 跳过  |

![vLLM 编译分段与动态形状符号守卫 tlparse 诊断视图](./images/vllm-torch-compile-flow.png '图 3：vLLM 中 TorchDynamo 捕获、按 Attention 分段切图、后端缓存与外层静态图包装链路（来源 vLLM 官方文档，Apache-2.0）')

![tlparse 中因模余条件分支泄漏出的动态 Guard 堆栈](./images/vllm-dynamic-shapes-tlparse.png '图 4：调试工具 tlparse 暴露出的由 % 128 对齐分支注入的符号 Guard 堆栈，这类隐蔽守卫常导致动态批大小反复重编（来源 vLLM 官方文档，Apache-2.0）')

图 4 揭示了一个隐蔽踩坑：代码里只要写了一句 `if num_tokens % 128 == 0:`，Dynamo 就会偷偷往 Guard 里塞一条模余约束，一旦出现第 129 个词元就失效重编。默认的 **0/1 步长特化** 还会把 `bs = 1` 单独特化，请求在单条与多条间波动时就会反复重编。

正因如此，vLLM 在顶层改用无 Guard 整图追踪：开启全局符号尺寸后不再为 `bs = 1` 单独特化，整网只编出 1 份通用 FX 图，把变长分发交给后端分段处理。

## 从 FX 到融合：AOTAutograd

拿到干净的 FX 图之后，编译器还要过 **AOTAutograd** 这一关。它先用不占物理显存的 **FakeTensor**（只保留形状、数据类型和设备）跑一遍抽象推演，确认张量维度严丝合缝。

接着执行 **Functionalization（函数化）**：把类似 `x.add_(y)` 的原位修改和切片别名重写成无副作用的 **Core ATen IR（核心张量中间表示）** 节点。这样后端就能放心重排算子与融合访存，不会改坏共享同一块显存的其他变量[^vllm-compile-doc]。

完成降级的 Core ATen IR 在 NVIDIA GPU 与华为昇腾 NPU 上走向不同的代码生成路线，整体分叉如图 5 所示[^ascend-compile-doc]。

![PyTorch 前端降级链及 GPU Inductor 与昇腾 AscendCompiler 后端分叉架构](./diagrams/02-compile-ir-and-backends.drawio '图 5：PyTorch 前端 FX 提取、splitting_ops 切段与 GPU/NPU 双端融合代码生成路径')

| 后端比较维度 | NVIDIA GPU（`TorchInductor`）          | Ascend NPU（`AscendCompiler`）             |
| :----------- | :------------------------------------- | :----------------------------------------- |
| 核心优化方式 | 全局分析与 **Loop Fusion（循环融合）** | 关闭 Inductor；FX 模式替换或 `npugraph_ex` |
| 产物运行形态 | 生成 Triton 或 CUDA 算子降 HBM 读写    | 替换为 CANN `aclnn` 或 NNAL 融合算子       |
| 共同调度边界 | 逐段出图，外层需 `CUDAGraphWrapper`    | 按 `splitting_ops` 切段，接 `ACLGraph`     |

在 GPU 上，`TorchInductor` 把相邻逐元素与归约算子直接编译成一段 Triton 代码。而在昇腾上，`vllm-ascend`（提交 `b776261e`）用 `GraphFusionPassManager` 在 FX 图上做模式替换，再交由 `npugraph_ex` 下发[^ascend-compile-doc][^ascend-pass]。

典型融合覆盖三类模式：规范化量化 `AddRMSNormQuantFusionPass` 与位置编码 `QKNormRopeFusionPass` 等。此外还有矩阵通信 `MatmulReduceScatterFusionPass` 等通道级替换。

## 为什么编译到头仍绕不开静态执行图

即便前后段算子融合得再干净，大模型里总有一类算子编译不动——注意力计算（如 PagedAttention 或 `AscendDSAV41Impl`）。它每一步都要按请求动态读取变长 KV 块表，无法静态展开成纯张量循环。

为此，vLLM V1 架构[^vllm-v1-blog]与 `torch.compile` 团队[^vllm-tc-blog]在工程上确立了 **`splitting_ops`** 分段方案（图 6）。夹在注意力之间的线性投影与 MLP 分别编译成独立产物并套上静态执行图，注意力算子则保持 Eager 动态调度，并通过自定义 Pass 进一步融合激活与量化。

这种设计也有明确边界：vLLM V1 靠分段编译加轻量调度拿到最高 1.7 倍吞吐提升，并把产物缓存进本地磁盘。但像注意力与量化全局融合 `AttnQuantFusionPass` 这类跨注意力界面的优化，就必须在关闭 `splitting_ops` 切段后才能看到整图[^vllm-tc-blog]。

下面的纯 CPU Python 脚本量化核算了 SwiGLU 的 HBM 访存降幅、0/1 特化重编次数以及 40 层模型的残余主机发射耗时：

```python
from dataclasses import dataclass

@dataclass
class FxNode:
    op: str
    name: str
    out_bytes: int

def trace_swiglu(batch: int, hidden: int, inter: int) -> list[FxNode]:
    bpe = 2
    return [
        FxNode("placeholder", "x", batch * hidden * bpe),
        FxNode("call_module", "w_gate", batch * inter * bpe),
        FxNode("call_function", "chunk", batch * inter * bpe),
        FxNode("call_function", "silu", batch * (inter // 2) * bpe),
        FxNode("call_function", "mul", batch * (inter // 2) * bpe),
        FxNode("call_module", "w_down", batch * hidden * bpe),
        FxNode("call_function", "add", batch * hidden * bpe),
    ]

nodes = trace_swiglu(batch=8, hidden=5120, inter=10240)
print(f"[FX Nodes] total={len(nodes)}, ops={[n.name for n in nodes]}")

B, D_HALF, BPE = 8, 5120, 2
unfused_bytes = B * D_HALF * BPE * 5
fused_bytes = B * D_HALF * BPE * 3

def eval_guards(batches: list[int], zero_one_spec: bool) -> int:
    seen, recompiles = set(), 0
    for bs in batches:
        key = ("spec_1" if bs <= 1 else "dyn_N") if zero_one_spec else "dyn_N"
        if key not in seen:
            seen.add(key)
            recompiles += 1
    return recompiles

re_01 = eval_guards([4, 8, 1, 16, 1], zero_one_spec=True)
re_sym = eval_guards([4, 8, 1, 16, 1], zero_one_spec=False)

n_layers, ops_eager, ops_fused = 40, 28, 10
eager_host_us = n_layers * ops_eager * 12.0
compiled_host_us = n_layers * ops_fused * 12.0
compiled_dev_us = n_layers * ops_fused * 8.5

print(f"[HBM Elementwise] unfused={unfused_bytes/1024:.1f}KB -> fused={fused_bytes/1024:.1f}KB (-{1 - fused_bytes/unfused_bytes:.0%})")
print(f"[Guard Recompiles] 0/1_spec={re_01} vs uniform_dynamic={re_sym}")
print(f"[40L V4.1-Flash] EagerHost={eager_host_us:.0f}us, CompiledHost={compiled_host_us:.0f}us vs Dev={compiled_dev_us:.0f}us ({compiled_host_us/compiled_dev_us:.2f}x)")
```

脚本输出证实，融合把逐元素访存削减了 40%，把主机发射耗时从 $13440\,\mu\text{s}$ 压到了 $4800\,\mu\text{s}$。但对比 $3400\,\mu\text{s}$ 的设备算力耗时，主机下发依旧占到设备执行时间的 1.41 倍：

```text
[FX Nodes] total=7, ops=['x', 'w_gate', 'chunk', 'silu', 'mul', 'w_down', 'add']
[HBM Elementwise] unfused=400.0KB -> fused=240.0KB (-40%)
[Guard Recompiles] 0/1_spec=2 vs uniform_dynamic=1
[40L V4.1-Flash] EagerHost=13440us, CompiledHost=4800us vs Dev=3400us (1.41x)
```

## 源码对照：分段后端与昇腾编译

在 `vllm`（提交 `99b0b0b0`）与 `vllm-ascend`（提交 `b776261e`）中，切分出来的每一段静态子图都交由对应的后端管理器按形状区间分别编译和缓存，核心类关系如图 8 所示[^vllm-pw][^ascend-ci][^ascend-pass]。

```mermaid caption="图 8：vllm@99b0b0b0 分段编译后端与 vllm-ascend@b776261e 融合通道类关系"
classDiagram
    class PiecewiseBackend {
        +compile_ranges
        +compile_sizes
        +RangeEntry
        +create_concrete_args()
    }
    class AscendCompiler {
        +compile_factors()
        +initialize_cache()
        +compile()
    }
    class GraphFusionPassManager {
        +AddRMSNormQuantFusionPass
        +QKNormRopeFusionPass
        +MatmulReduceScatterFusionPass
    }
    class npugraph_ex_compile {
        +patched_get_compiled_gm()
        +skip_cache_if_triton()
    }

    PiecewiseBackend --> AscendCompiler : delegates Ascend subgraph
    AscendCompiler --> GraphFusionPassManager : runs FX pattern passes
    AscendCompiler --> npugraph_ex_compile : lowers to NPU backend
```

昇腾编译通道在 `npugraph_ex_compile` 里有一项关键工程保护[^ascend-ci]。若子图包含自定义 Triton Ascend 算子，代码会依赖进程内临时注册的 `kernel_side_table` 跳转索引，跨进程读取缓存必定报错。因此编译器会检测 `triton_kernel_wrapper` 并跳过磁盘缓存，必要时可用 `force_eager` 把疑难算子切出编译图。

要彻底拿掉残余的数千微秒主机发射墙，光靠编译器融算子已经到头，必须把整段指令拓扑固化到驱动侧实现单次发射。[第 3 章：CUDA Graph 原理：流捕获、四边界与双模](../03-cuda-graph-fundamentals/)将确立设备静态执行图的核心契约。
