## 为什么值得自己写一遍

读源码时很容易产生「我懂了」的错觉。但下面这些问题，不自己写一遍很难答对：

- batch 是 5，桶有 `[2, 4, 8]`，命中哪个？padding 多少？
- 同一个 batch，LoRA 数从 0 变成 1，还能命中吗？
- 桶上限 8，来了个 batch 9，会发生什么？**会报错吗？**

## 练习一：实现兼容性检查

把第 05 篇那六项条件写出来。这是全部练习的基础。

```python
def is_compatible(desc, req):
    """desc: 一张已捕获的图；req: 本轮 batch。返回 True/False。

    六项条件（顺序与 vLLM 源码一致）：
      1. desc.uniform_token_count 为 None，或与 req 相等
      2. desc.max_query_len 为 None，或（req 的不为 None 且 desc 的 >= req 的）
      3. desc.num_reqs 为 None，或 >= req.num_reqs
      4. desc.num_tokens >= req.num_tokens
      5. desc.num_active_loras == req.num_active_loras      ← 相等，不是 >=
      6. desc.num_ubatches == req.num_ubatches              ← 相等，不是 >=
    """
    raise NotImplementedError
```

**陷阱**：第 2 条不是简单的 `>=`。源码注释写着「a caller that does not track max_query_len must not match one that does」——图有约束而调用方传 `None` 时，** 不能匹配**[^vllm-dispatch-code]。

## 练习二：实现 dispatch

```python
def dispatch(graphs, req):
    """按顺序找第一个兼容的图；都不兼容时返回 eager 描述符（cg_mode='NONE'）。"""
    raise NotImplementedError
```

**陷阱**：是「第一个够大的」，不是「最接近的」，也不是「最大的」[^vllm-dispatch-code]。所以候选的顺序会影响 padding——这正是源码把 decode 图插到队首的原因。

## 练习五：设计桶

给定一个 batch 分布，选一套桶使「平均 padding 浪费」最小，同时图的数量不超过 8。

```python
WORKLOAD = (
    [1] * 600 +            # 60% 是单请求 decode
    [2] * 150 + [3] * 80 + [4] * 60 +
    [8] * 50 + [16] * 30 + [32] * 20 + [64] * 10
)

def choose_buckets(workload, max_graphs=8):
    """返回一个桶列表（升序）。目标：命中率高、padding 少、图不超过 max_graphs。"""
    raise NotImplementedError
```

`toy.py` 的参考实现对照了三套方案：

```
workload：1000 轮，60% 是 batch=1，长尾到 64

方案                               图数      命中率     平均 padding 浪费
均匀 [8,16,24,32,40,48,56,64]       8   100.0%             71.8%
2 的幂 [1,2,4,8,16,32,64]           7   100.0%              2.0%
贴着分布 [1, 2, 3, 4, 8, 16, 32, 64]    8   100.0%              0.0%
```

**均匀分桶是最差的**：60% 的请求是 batch=1，却被 padding 到 8，白算 87.5%——平均浪费高达 71.8%。而贴着实际分布选桶，用同样 8 张图把浪费压到 0（因为桶恰好落在实际出现的 batch 上）。

三套方案的命中率都是 100%，差别**全在 padding**。这说明选桶时「能不能命中」往往不是难点，「命中之后浪费多少」才是。

这就是「小 batch 密、大 batch 疏」的来由：**桶应该贴着负载的分布，而不是贴着数轴**。

## 代价与边界

- 这些练习只复刻**匹配逻辑**。真实系统还要处理捕获时机、显存、内存池、attention 后端的支持级别、DP/TP 的协调——那些都不在这里。
- `WORKLOAD` 是人造分布。真实负载要自己采样，而且会随时间变化（白天和夜里的 batch 分布可能完全不同）。
- 练习里的「padding 浪费」只算 token 数，不等于实际算力浪费：padding 的位置也要过完整的模型层。
- 本机没有 GPU/NPU，这里不运行任何真实捕获，也不给时间数字。
